# 03: Mali-G610 / RK3588 device-specific improvements (Orange Pi 5)

Status: complete

## Top conclusions

Ranked by expected gain on the Orange Pi in a real deployment (camera-paced frames, default OS
settings). Every gain below is an estimate unless marked measured; nothing was run on the GPU.

1. **Run the detector's CPU work on A76s at full clock (finding 3). Pursue.** The kernel defaults to
   `ondemand` (up_threshold 95, 10 ms sampling); the A76s were at 600 MHz when sampled, and nothing in
   the tree sets affinity, so pool workers and the driver thread can run on A55s. Every published Pi
   number used pinned `performance` governors. Estimated 1-3 ms of latency per frame at camera rates.
   Test with no code: `performance` on policy4/6 and `taskset -c 4-7` + `APRILTAG_CPU_THREADS=4`,
   paced with `bench_multiqueue --fps 60`. Then add an affinity knob, or uclamp under `schedutil`.
2. **Ingest: hardware MJPEG decode (jpegd via MPP, present on this BSP kernel and already bundled by
   the product) into an imported dma-buf, or a luma-only libjpeg-turbo decode written straight into the
   mapped gray buffer (finding 6). Pursue, caller side first.** Removes several ms of A76 decode (still
   unmeasured) plus the 0.19 ms copy (measured). The library gap is a row stride / plane offset in
   `ImportDmaBufFrame`.
3. **GPU power-down between paced frames (finding 1). Measure first.** `coarse_demand`, 800 us
   shader power-off and 10 ms idle hysteresis mean every frame at <= 60 fps starts from a powered-down
   GPU, which no back-to-back benchmark sees. A/B `power_policy=always_on` with
   `bench_multiqueue --fps 30/60`.
4. **Fence-completion path (finding 2). Measure first.** GPU IRQs are handled on CPU0 (an A55), and
   the menu governor's `cpu-sleep` state has a 220 us exit latency. The fence-spin rejection was
   desktop-only. Try moving the IRQs to the A76s and disabling `cpu-sleep`, then a hybrid
   wait-then-spin if that helps. Estimated tens of us to ~0.3 ms per frame.
5. **Profile the G610 before more shader work (finding 5). Pursue.** The kernel has
   `CONFIG_MALI_BIFROST_GATOR_SUPPORT=y`, so Streamline/gatord and libGPUCounters should work;
   g24p0 lacks `pipeline_executable_properties`, so register counts must come from malioc. The
   counters decide findings 4 and 10.
6. **Atomics (finding 4). Measure after 5.** Key extents copies by `gl_CoreIDARM` (core mask confirmed
   `0x50005`, so use a popcount rank, never `& 7`), and have `blob_diff` reserve each thread's points
   with one `atomicAdd`. Estimated 0-0.1 ms each.
7. **Rank-by-counting for small blobs in the sort (finding 10). Measure first.** It trades Mali's
   barrier rounds for single-cycle uniform shared loads. Needs the blob-size histogram and a
   Mali barrier-removal ceiling. Estimated 0-5% of GPU time.
8. **Low or none:** `-mtune=cortex-a76` / NEON for the tail (finding 11: memory-latency-bound, exact
   double math); global priority, scheduling controls, a second queue (finding 12: no single-stream
   gain; the multi-stream gain is already measured); g29p1 / `CMAR_OPTIMIZE_FOR_LATENCY` (10-minute
   probes, low expectation).
9. **Rejected:** RGA (finding 7: its averaging is not upstream's point-sampled decimation, it adds an
   ioctl hop, and the GPU already reads YUYV/NV12 luma) and the NPU (finding 8: no stage fits; a
   4-8 ms per-call floor vs 2.7 ms for all of `Detect()`). The ISP/CSI path (finding 9) applies only
   if a CSI camera is used.

**Measurement hygiene found on the board:** `/opt/lumenvision/Server` was using ~175% CPU in the
background, and policy0 (A55) was left at min = max = 1.8 GHz. Stop the former and check the latter
before any Pi A/B.

## Findings

### 1. The GPU powers down between frames at real camera rates; the benchmarks never see it (Mali)

- **Idea:** measure, and if needed avoid, per-frame GPU power-up latency when frames arrive at
  30-120 fps instead of back to back. Orange Pi only.
- **Mechanism:** the kbase CSF driver is in `coarse_demand` with `mcu_shader_pwroff_timeout` = 800 us
  and `idle_hysteresis_time` = 10 ms, and runtime PM is `auto` (the GPU reads `suspended` when idle).
  So shader cores power off ~0.8 ms after the GPU goes idle, and the whole GPU (MCU firmware, then the
  power domain via runtime PM) goes down after 10 ms idle. Every in-tree number was taken back to back:
  `Detect()` 2.70 ms at ~381 fps (PERFORMANCE.md 8g), where the GPU idles only during the ~1.5 ms CPU
  tail (enough to trip the 0.8 ms shader power-off on every serial frame, but never the 10 ms one), or
  not at all with `FramePipeline`. A camera at 60 fps leaves the GPU idle ~14 ms per frame, at 30 fps
  ~30 ms, so every frame starts from a powered-down GPU: firmware wake, shader-core power-up, L2 cold.
  The GPU IRQ line that carries power/cache events (irq 160) has counted 279,313 against 42,114 on the
  job/CSF line (irq 162) since boot; that 6.6:1 ratio is consistent with frequent power transitions, but
  the boot-time workload is unknown so it is not proof.
- **Expected gain:** unknown, estimate only. Wake costs on Mali CSF parts are typically tens of us
  (shader cores) to ~1 ms (MCU reboot plus runtime resume), so per frame it ranges from noise to the
  same order as the 126 us host overhead the pre-recording work just removed half of. It affects
  latency per frame at camera rates, not the saturated throughput figures.
- **Cost and risk:** measurement is free. Fixes are deployment settings, not code: `echo always_on >
  /sys/class/misc/mali0/device/power_policy` (costs idle power), or raise `mcu_shader_pwroff_timeout` /
  `idle_hysteresis_time` past the frame period. Root only, so the library can only document it. A
  "keep-alive" dummy submission from the library would be the wrong fix.
- **Prior art:** none. The tree pins governors and measures back to back; summary item C2 covers
  frequency governors, not power policy.
- **Verdict:** **measure first, cheap.** Stop the background `Server` process, then `bench_multiqueue
  --streams 1 --fps 30`, `--fps 60`, `--fps 120` and unpaced, reading `latency_med_ms` /
  `latency_p99_ms`, once with `coarse_demand` and once with `always_on` (restore afterwards). If the
  paced latency exceeds the unpaced `Detect()` by more than ~0.1 ms and `always_on` removes it, document
  the setting in PERFORMANCE.md section 1 and in the deployment notes.

### 2. The fence-completion path runs through an A55 and a 220 us idle state (Mali / RK3588 CPU side)

- **Idea:** shorten the time from "GPU finished" to "`Detect()` returns" on the Pi: route the GPU
  interrupt to an A76, keep the waiting core out of `cpu-sleep`, or spin on the fence for the last part
  of the wait. Orange Pi only.
- **Mechanism:** `Detect()` blocks in `vkWaitForFences` for the whole ~2.5 ms GPU phase (one
  submission per frame, `Lane::SubmitPersistentAndWait`). On this board the menu cpuidle governor has a
  `cpu-sleep` state with **exit latency 220 us, target residency 1 ms**, so a ~2.5 ms predicted idle
  selects it. The GPU interrupts have effective affinity **CPU0, an A55**, which is itself idle most of
  the time (cpu0's `cpu-sleep` was entered 1.59 M times; 36% of those entries were "above", i.e. the
  sleep was too deep for the actual idle). So completion is: CPU0 leaves `cpu-sleep` (up to 220 us),
  kbase handles the CSF interrupt at A55 speed, then wakes the waiter, whose core may also need up to
  220 us. The RX 9060 XT figure for this gap is 137 us ("submit to first span plus last span to fence
  return", PERFORMANCE.md 8e); nobody has broken it out on the Pi, where `gpu.submit_wait` hides it.
- **New evidence vs the rejection:** the fence-spin experiment (commit `6917a51`, PERFORMANCE.md 8e)
  was measured **only on the RX 9060 XT under Windows**, where it did nothing. The Pi has a different
  OS, a 220 us idle state and the IRQ pinned to a little core, so that result does not transfer.
- **Expected gain:** estimate 0-0.3 ms per frame (0-10% of `Detect()`), declared worst case ~0.44 ms
  (two 220 us exits in series). Typical exits are well below the declared worst case, so the honest
  expectation is tens of us to ~0.1 ms. It matters most for single-camera latency; at GPU saturation
  (2-4 streams) the queue is never empty and the gap is hidden.
- **Cost and risk:** three independent options, cheapest first. (a) `echo 4-7 >
  /proc/irq/{160,161,162}/smp_affinity_list` (root, deployment setting, no code). (b) Disable `cpu-sleep`
  on the A76s while detecting: per-CPU `pm_qos_resume_latency_us` or `/dev/cpu_dma_latency` (root, or a
  udev rule granting the group; the library could open `/dev/cpu_dma_latency` if writable and write
  e.g. 100 us, which is automatically released when the fd closes). (c) Hybrid wait in
  `Lane::SubmitPersistentAndWait`: `vkWaitForFences` with a timeout of the previous frame's GPU time
  minus ~0.3 ms, then poll `vkGetFenceStatus`. Burns at most ~0.3 ms of one core per frame. Whether
  libmali's `vkGetFenceStatus` reads a firmware-written sync word (bypassing the IRQ entirely) or asks
  kbase (still needs the IRQ) is **unverified**; (c) helps the waiter's own wake-up either way. No effect
  on output.
- **Prior art:** fence spin rejected on the desktop only (above). IRQ affinity and cpuidle never
  examined.
- **Verdict:** **measure first**, no code needed for (a) and (b): on the Pi with governors pinned and
  `Server` stopped, `apriltag_vulkan_validate --profile` ABBA with the IRQs on CPU0 vs CPU4-7, then with
  `cpu-sleep` disabled vs enabled (`/sys/devices/system/cpu/cpu*/cpuidle/state1/disable`), reading
  `gpu.submit_wait` minus the GPU-track span sum (the tracer already places GPU spans on the host
  timeline). Build (c) only if (b) shows a gain, since (c) is the in-library way to get the same effect
  without root.

### 3. big.LITTLE: nothing in the tree places threads, and `ondemand` runs the tail at low clocks (RK3588 CPU)

- **Idea:** keep the detector's threads (caller, `gpu-driver`, `quad-worker`, `tag-worker`,
  `pose-worker`) on the A76s and make sure the A76s are clocked up while they run. Orange Pi only (any
  big.LITTLE target).
- **Mechanism:** (i) `grep` finds no affinity, `sched_setaffinity`, `SCHED_*` or nice call anywhere
  in the library; every `WorkerPool` defaults to `hardware_concurrency()` = 8, so each pool has workers
  that the kernel may run on the four A55s (capacity 405 vs 1024, in-order, max 1.8 GHz vs 2.352 GHz).
  `WorkerPool::DrainBatch` (`WorkerPool.cpp:43-48`) claims items with an atomic counter, which balances
  throughput, but the batch ends when the slowest claimant finishes: an A55 that claims one of the last
  quads holds the join (`pool.join_wait`) for ~2.5x that quad's A76 time. `TagDecoder::Decode` and
  `QuadDecode::Decode` claim in blob order, not largest first (`TagDecoder.cpp:98`,
  `QuadDecode.cpp:480`). PERFORMANCE.md 8e's "load is balanced" was measured on the desktop's
  homogeneous 12 threads. (ii) With `ondemand`, `sampling_rate` 10 ms and `up_threshold` 95, a bursty
  workload (2.5 ms blocked in the fence wait, then ~1.5 ms of tail spread over 8 threads) rarely shows
  95% load in a 10 ms window, so the A76s stay low: policy4 was at **600 MHz** when sampled. At 30-60
  fps it is worse (a few % utilisation). The tail and the 126 us host overhead then run up to ~3.9x
  slower than in every in-tree measurement, which were all taken with governors pinned to
  `performance` (PERFORMANCE.md 8b/8c/8g). (iii) The scheduler's capacity-aware wake-up (asymmetric
  capacities, EAS inactive because the governor is not `schedutil`) places a thread whose average
  utilisation is low on any CPU it "fits", and a thread that sleeps 2.5 ms of every 4 ms has low
  utilisation, so the `gpu-driver` thread and the caller can land on A55s.
- **Expected gain:** (ii) is the large one at camera rates: tail 0.44 + 0.79 ms (PERFORMANCE.md 3,
  pinned) could be 2-4 ms with the A76s at 408-600 MHz, so pinning or clamping is worth on the order of
  1-3 ms of latency per frame in a default-governor deployment. This is an estimate from the frequency
  ratio, not a measurement. (i) and (iii) are smaller: a straggler quad on an A55 costs roughly one quad's
  refine time (tens of us), the driver thread on an A55 perhaps 1.5-2.5x of 126 us.
- **Cost and risk:** (a) Zero-code check: `taskset -c 4-7` with `APRILTAG_CPU_THREADS=4` vs default.
  (b) Library option: an `APRILTAG_CPU_AFFINITY=<cpulist>` knob (or reading the cpus with the highest
  `cpu_capacity` from sysfs) applied with `pthread_setaffinity_np` in `WorkerMain`, the `gpu-driver`
  thread and, optionally, the caller. Default thread count = number of max-capacity CPUs, not
  `hardware_concurrency()`. ~40 lines, no output change. (c) Clocks: if the deployment switches to
  `schedutil`, the library can set `uclamp.min = 1024` on its own threads with `sched_setattr`
  (`sched_util_clamp_min` is 1024 here), which makes schedutil run the A76s at full speed only while the
  detector runs and makes EAS prefer the big cores, without pinning the whole system to `performance`
  (whether an unprivileged process may raise its own `uclamp.min` on this kernel is **unverified**).
  Under `ondemand` there is no per-process lever; `performance` on policy4/policy6 is the fix (summary
  item C2 already recommends it, rapidtag measured 123 -> 211 fps on a QCS6490).
- **Prior art:** summary C2 (governors) and C7 ("pin CPU-tail workers to the A76s"), both proposed,
  neither measured. OPTIMIZATION_NOTES "Pipelining the CPU tail" swept `APRILTAG_CPU_THREADS` 1-8 for
  the old pipelined detector (minimum at 6) but never with affinity. New here: the board facts above
  (ondemand thresholds, 600 MHz observed, no placement code) and the observation that every published
  Pi number assumes pinned governors.
- **Verdict:** **pursue (a) now, then (b).** Measure `bench_multiqueue --streams 1 --fps 60` latency
  with default governors vs `performance` on policy4/6 to put a number on (ii), then `taskset -c 4-7` +
  `APRILTAG_CPU_THREADS=4` vs default with `apriltag_vulkan_validate --profile` (read `pool.join_wait`
  and `pipeline_total`). Ship (b) only if `taskset` shows a gain; also try ordering
  `TagDecoder::ParallelFor` largest-first only after affinity is fixed.
- **Two more facts for this finding:** (1) `ondemand` is the **kernel's compiled-in default**
  (`CONFIG_CPU_FREQ_DEFAULT_GOV_ONDEMAND=y` in `/boot/config-6.1.115-vendor-rk35xx`), so a fresh image
  behaves like this; `CONFIG_UCLAMP_TASK=y` and `CONFIG_ENERGY_MODEL=y` are set, so the
  schedutil + uclamp route in (c) is available on this kernel. (2) Pool workers wake through a
  `std::condition_variable` (`WorkerPool.cpp:58`); a worker whose core sat in `cpu-sleep` (220 us exit
  latency) during the 2.5 ms GPU phase starts its share late. Dynamic claiming hides part of that (the
  caller and awake workers keep draining), but with ~75 quads and a ~0.8 ms `tag_decode` a late worker
  is a visible fraction. The tracer already shows it: `pool.drain`'s arg is the number of items a thread
  claimed, and a thread that claims 0 woke too late. A short bounded spin before blocking in
  `WorkerMain` (tens of us, only while frames are back to back) is the in-library fix; measure the
  zero-claim rate first.

### 4. Atomics on the G610: key the extents copies by shader core, and batch `blob_diff`'s appends per thread (Mali)

- **Idea:** (a) choose the extents accumulator copy by the shader core that runs the workgroup
  (`gl_CoreIDARM`) instead of by `gl_WorkGroupID.x & 7`; (b) let each `blob_diff` thread reserve all
  of its 1-4 boundary points with one `atomicAdd(counter, n)` instead of up to four `atomicAdd(counter,
  1)`. Mali first; (b) is valid everywhere.
- **Mechanism (a):** `reduce_extents_hash_body.glsl:33` picks `copy = gl_WorkGroupID.x & 7`. Workgroups
  are spread over all four cores, so every copy is updated from every core, and each contended line
  migrates between the cores' L1s through L2 snoops. Arm's guide (research/07 BP-3): "Atomics are
  efficient when a shader core controls the necessary cache line in its L1", and the
  `VK_ARM_shader_core_builtins` spec names per-core instances of an atomic data structure as the
  intended use. **New fact from the board: `shaderCoreMask` = `0x50005`, core ids 0, 2, 16, 18**, so
  `gl_CoreIDARM & 7` would put two cores on the same copy and leave copies empty. A dense rank is one
  instruction: `rank = bitCount(kCoreMask & ((1u << gl_CoreIDARM) - 1u))` with `kCoreMask` a
  specialization constant from `VkPhysicalDeviceShaderCoreBuiltinsPropertiesARM::shaderCoreMask`.
  Keep K = 8 so `merge_extents.comp` is unchanged: `copy = rank * 2 + (gl_WorkGroupID.x & 1)`.
  Integer min/max/add are associative, so the result is bit-identical.
- **Mechanism (b):** `blob_diff_body.glsl:32-41` issues one `atomicAdd(counter, 1u)` per emitted
  point on a single global address, up to four per thread, from all four cores; on Mali that is the
  worst case BP-3 describes (one line, every core). Counting the thread's `want*` flags first and
  reserving `n` slots once removes every second, third and fourth atomic of a thread without a barrier
  or shared memory (which is what made the earlier aggregation proposals risky on Mali). Output order
  changes, but the tree already compares quads order-insensitively, and item 13 of OPTIMIZATION_NOTES
  found zero genuine `theta_key` ties, so canonical quads stay identical.
- **Expected gain:** (a) bounded by the extents span: 0.221 ms after int64 atomics vs a 0.062 ms
  plain-store bound (OPTIMIZATION_NOTES third pass items 3-4); per-core keying removes line migration
  but not the multi-cycle atomic issue itself, so estimate 0-0.08 ms (0-3% of `Detect()`). (b) The
  `boundary` span is 0.36 ms with 1.09x DRAM sensitivity, i.e. not bandwidth; the saving scales with the
  mean number of points per emitting pixel, which nobody has measured (estimate 1.2-1.8). Estimate
  0-0.1 ms. Both are estimates, not measurements.
- **Cost and risk:** (a) ~20 lines: enable `shaderCoreBuiltins` (the tree already enables
  `VK_KHR_shader_atomic_int64`, so "zero optional features" is no longer literal), a third variant of
  the atomic64 shader, the mask as a spec constant, `APRILTAG_VK_FORCE_NO_CORE_ID=1` for A/B. Present on
  g24p0, g29p1 and PanVK. (b) ~10 lines in one shader, all devices.
- **Prior art:** (a) proposed in research/07 BP-3 and summary A6(c), never built; A6(b) (copy by lane)
  was built and lost on both devices (+5.4% on Mali, OPTIMIZATION_NOTES item 11) because it broke the
  same-blob locality of append order, which per-core keying keeps (all lanes of a workgroup still hit
  one copy). A6(a) (64-byte padding) was a coin flip on Mali (item 16). (b) Not proposed before: the
  rejected variants were *subgroup* aggregation (RX only, DESIGN.md) and *shared-memory* aggregation
  (research/05 idea 5, never built, flagged for its barrier).
- **Verdict:** **measure first, cheap A/Bs.** Best preceded by the counter capture in finding 5
  (`LS atomic` cycles and L1 snoops on the `extents` and `boundary` spans say whether either is
  migration-bound). Then ABBA on the Pi, 12+ rounds, `--dump-quads` identical, reading the `extents`
  and `boundary` spans and GPU total.

### 5. Look inside the GPU before more shader work: the tools exist for this board (Mali)

- **Idea:** replace the remaining "deliberately incorrect build" bounds with hardware counters and
  static register reports. Mali only.
- **Mechanism / facts:** (1) **Hardware counters are compiled into this kernel**:
  `CONFIG_MALI_BIFROST_GATOR_SUPPORT=y`, `CONFIG_MALI_CSF_SUPPORT=y`, `CONFIG_HW_PERF_EVENTS=y`. So
  Arm Streamline with an on-board `gatord` (prebuilt aarch64 binary from Arm Performance Studio, not
  installed today) should give the G610 counter set plus CPU PMU counters on one timeline;
  libGPUCounters (CSF backend, "Arm commercial driver" only) can do the same from inside
  `apriltag_vulkan_validate`. PERFORMANCE.md section 9's "Mali exposes no external GPU profiler at all"
  is wrong for this board. (2) **g24p0 does not expose `VK_KHR_pipeline_executable_properties`**
  (checked in this session's vulkaninfo), so register and spill counts must come from Arm's offline
  compiler (`malioc`, part of the same free Performance Studio, runs on Windows; not installed on this
  PC either). (3) `perf` is usable on the board (`CONFIG_PERF_EVENTS=y`) but not installed.
- **What each tool would settle:**

  | Open question | Tool and counter | Decides |
  | --- | --- | --- |
  | Are `extents` / `boundary` bound by atomic issue or by line migration? | Streamline: LS atomic-access cycles, L1 snoops from other cores, per span | finding 4 (a) and (b) |
  | Does labelling miss the 1 MB L2 (parent 1.0 MB + thresholded 0.25 MB at 1280x800 d2)? | LS bytes read from external memory vs from L2 during `uf_merge` | research/07 conclusion 8 (run-compressed parents) |
  | Is any shader above 32 work registers (half occupancy) or spilling? | `malioc -c Mali-G610` on the SPIR-V with Mali's spec constants (wg1d 128, 2D 8x8, sort 256 threads, `kLocalCap` 2048) | whether any register work is worth doing |

- **Expected gain:** none directly; it is the measurement that ranks findings 2-4 and research/07's
  open items. Honest prior for the register audit: these shaders are short and scalar (the largest,
  `sort_points_local_body.glsl`, is 143 lines with no big arrays in registers), so they are probably
  all under 32 registers. The llama.cpp 17-24x register story (research/07) came from large tiled
  matmul kernels and does not transfer. Expect malioc to rule register pressure out rather than find a
  win; it is still an hour's work.
- **Cost and risk:** installing Performance Studio on the PC and copying `gatord` to the Pi (the user's
  call; not done here). Counter capture perturbs timing slightly; use it for attribution, not for
  headline numbers (the same caution as the timestamp spans, which cost ~9% on Mali).
- **Prior art:** proposed in research/07 (malioc, libGPUCounters, Streamline entries) and summary 0.3;
  not done. New: the kernel config and the missing `pipeline_executable_properties` were verified on
  the board, so the route is known to be open and the alternative is known to be closed.
- **Verdict:** **pursue**, before building findings 4 or any further shader change.

### 6. Ingest: hardware MJPEG decode into an imported dma-buf, or luma-only software decode into the mapped buffer (RK3588)

- **Idea:** end to end, the biggest remaining Pi cost sits before `Detect()`: getting a camera frame
  into the gray buffer. Two routes, by camera mode. Orange Pi only.
- **Mechanism, hardware route (UVC MJPEG):** the board has the decoder and its kernel driver
  (`jpegd@fdb90000` okay, `/proc/mpp_service/jpegd`, `/dev/mpp_service` group `video`), and the product
  already ships `librockchip_mpp.so.1`. MPP decodes into dma-bufs (DMA heap or caller-supplied buffers).
  `GpuDetector::ImportDmaBufFrame` (`GpuDetector.h:209`) already imports a dma-buf once and reads it in
  place, and PERFORMANCE.md 8d measured that path on this board (dma-heap buffer, identical quads,
  `Detect()` 2.79 -> 2.60 ms). Device-written buffers need no CPU cache maintenance, unlike the UVC
  vmalloc buffers that needed `dc civac`. Two gaps in the API: (1) there is no row stride or plane
  offset: `decimate` assumes `width` bytes per row from offset 0, while MPP output has a horizontal
  stride (often equal to the width at 1280/1600/1920, but not guaranteed), and the luma plane of NV12
  or NV16 (UVC MJPEG is usually 4:2:2) is at offset 0 only by convention; (2) MPP recycles a small
  buffer ring, so the import cache keyed by pointer (`imported_frames_`) must be sized for the ring.
  RK3588 jpegd is specified at 560 Mpx/s (research/07), ~1.8 ms of decoder time per 1280x800 frame,
  on its own block, in parallel with GPU and CPU.
- **Mechanism, software route (no MPP):** decode with libjpeg-turbo straight into the mapped gray
  buffer (`gray_buf_` is `DeviceLocalMapped` = memory type `0x7`, write-combined, no flush needed) with
  `out_color_space = JCS_GRAYSCALE`. For a YCbCr JPEG, libjpeg-turbo then skips chroma IDCT, upsampling
  and colour conversion, and the 0.19 ms memcpy (2.79 vs 2.60 ms above) also goes. Needs an API that
  hands the caller the mapped pointer (e.g. `uint8_t *GpuDetector::FrameBuffer()` plus a `Detect()`
  without a source), or a dma-heap `system` buffer the caller writes and then `DMA_BUF_IOCTL_SYNC`s (the
  system heap implements CPU-access sync, unlike uvcvideo's exporter). `/dev/udmabuf` is **not**
  available (`CONFIG_UDMABUF` unset), so wrapping malloc memory is not an option, and g24p0 has no
  `VK_EXT_external_memory_host`.
- **Expected gain:** hardware route: removes software MJPEG decode from the A76s entirely (several ms
  per frame per research/07 and PhotonVision #1497; the A76 decode time is still **unmeasured**) plus
  the 0.19 ms copy. Software luma-only route: decode time falls by the chroma share (estimate 25-40%,
  not measured) plus the copy. Either is larger than any GPU-side item in this file, but only for the
  MJPEG camera mode.
- **Cost and risk:** hardware route: ~100 lines of stride/offset support in `decimate` and the import
  API; the MPP glue belongs in the caller (the product already links MPP). BSP kernel only (mainline has
  no RK3588 JPEG decoder, research/07). Hardware IDCT luma may differ by 1 from libjpeg-turbo; the
  GPU-vs-CPU gate is unaffected (same input to both). Software route: luma of a `JCS_GRAYSCALE` decode is
  the JPEG's Y channel, which differs by rounding from `cvtColor(BGR2GRAY)` of a colour decode; the gate
  is unaffected, but live detections can move by sub-pixel amounts.
- **Prior art:** summary C1 and research/07 (MPP, Jellyfin's OpenCL import, the UVC vmalloc hazard);
  PERFORMANCE.md 8d built dma-buf import and `decimate_yuyv`. New here: the board's decoder and
  libraries confirmed present, the stride/offset gap in `ImportDmaBufFrame`, the luma-only software
  decode, and udmabuf's absence.
- **Verdict:** **pursue, starting in the caller.** On the Pi (with `Server` stopped) time
  `tjdecompress` to gray vs to BGR for a 1280x800 and a 1600x1200 MJPEG frame on one pinned A76; then
  add stride/offset to `ImportDmaBufFrame` and prove the MPP path with `dmabuf_import_test` (same quads
  as the copy path, every frame).

### 7. RGA: no tangible benefit for this pipeline (RK3588) - reject

- **Idea:** use the RGA (2 x RGA3 + 1 x RGA2, all probed: `rga3 hw_version 3.0.76831`, `rga2
  3.2.63318`) for decimation, YUYV/NV12 -> gray, or crop.
- **Why not:** (1) Decimation: `decimate.comp` point-samples the top-left pixel of each block
  (`QuadDecode.cpp:568-569`), matching upstream's integer decimation; RGA scale-down averages (RGA3 box,
  RGA2 average/bilinear) and the two core types sample with different offsets (research/07 librga
  entry), so the result is neither what libapriltag decimates nor deterministic across cores. (2) Colour:
  the GPU already reads luma from YUYV in `decimate_yuyv`, and the NV12/NV16 luma plane needs no
  conversion. (3) Crop: a crop is an offset plus a stride for the GPU (finding 6), not a copy. (4) Each
  RGA job is an ioctl round trip with its own fence and cache maintenance in front of a GPU stage
  (`decimate` + threshold) that is ~4% of the Mali frame. PhotonVision recorded RGA crashes (research/07).
- **Expected gain:** none; adds latency.
- **Verdict:** **reject.** Revisit only if a camera delivers a format the GPU cannot read directly
  (e.g. AFBC-tiled output), which none of the current paths do.

### 8. NPU (RKNPU2, 3 cores, 6 TOPS): no stage of this pipeline fits it (RK3588) - reject

- **Idea:** offload a vkapriltag stage to the NPU, or use it for ROI proposals.
- **Why not, per stage:** the GPU stages are union-find with atomics, hashing, per-blob sorting and
  compaction: integer, data-dependent, irregular; the NPU runs dense int8/fp16 conv and matmul. The only
  expressible part is preprocessing (decimation is a strided slice; `block_minmax` / `block_filter` are
  max/min pooling), which is ~4% of the Mali frame, and the threshold compare needs exact integer
  arithmetic that int8 quantisation does not guarantee. Every NPU call also pays a driver round trip:
  published small-model latencies on RK3588 are ~4-8 ms per inference on one core (ResNet18 4.09 ms;
  a small CNN 7.9 ms through go-rknnlite), against 2.7 ms for the whole `Detect()`.
- **ROI proposals:** the product already ships an RKNN YOLO11 tag model; the previous round put YOLO11
  at ~23 ms and YOLOv8n at ~13.6 ms on this NPU. A proposal that arrives 4-8x later than a full-frame
  detection cannot speed up a frame. Run asynchronously on the previous frame, it helps only when
  full-frame detection is itself the bottleneck (e.g. decimation 1 at 1600x1200), and it misses newly
  appearing tags. That is product policy (summary D2/D3 crop lists), not a detector speedup.
- **Expected gain:** none for the detector.
- **Prior art:** rejected in summary section 2 on the YOLO latencies; the per-stage reasoning and the
  board facts (NPU is DRM `card1`/`renderD129`, RKNPU 0.9.8; no system-wide `librknnrt`) are new.
- **Verdict:** **reject.** The NPU's useful role is running the product's other models concurrently
  without taking GPU time.
- Sources: https://tinycomputers.io/posts/rockchip-rk3588-npu-benchmarks.html ,
  https://forum.radxa.com/t/go-rknnlite-go-language-bindings-for-rknn-tookit2/20608

### 9. ISP / CSI cameras: the cleanest zero-copy source, but no CSI camera here (RK3588) - conditional

- **Idea:** with a MIPI-CSI sensor, rkisp DMA-writes NV12 into dma-bufs with correct sync
  (research/07), so a frame reaches `ImportDmaBufFrame` with no CPU touch.
- **Facts:** `rkisp@fdcb0000` and `rkispp` nodes are enabled, but no `/dev/video*` exists now, and FRC
  deployments of this board mostly use USB cameras. The ISP downscaler filters, so it must not stand in
  for `decimate` (same reasoning as finding 7), and decode would then sample the low-resolution image
  (upstream decodes on the full-resolution frame).
- **Expected gain:** for a CSI deployment, finding 6's hardware route without the decoder.
- **Verdict:** **conditional.** Library side needs only finding 6's stride/offset support; not worth
  effort until a CSI camera is in use.

### 10. Valhall shader tuning: an audit of what is left (Mali)

Checked against the Valhall rules in research/07 (BP-1..BP-8, the G610 counter guide) and the
current shaders. Most of it is already compliant or already measured; one idea is new.

| Rule | State in the tree | Verdict |
| --- | --- | --- |
| No integer divide (Valhall has none) | `grep` of `library/shaders`: the only runtime `/` on integers is `build_indirect_args.comp:28` (a handful of threads); `uf_merge` went 2D to avoid one; sort enumeration uses shifts | compliant |
| Barriers / shared memory cost on Mali | `uf_merge` runs barrier-free on unified memory (`kMergeFlagMode` 1, OPTIMIZATION_NOTES item 14); `sort_points_local` 256 threads measured best; `scan_block` uses `scan_wg` 1024 + shared + barriers, 16x the guide's 64 ceiling, but `blob_scan` is ~10 us in total | compliant / too small to matter |
| Workgroup size, 16-wide warps | wg1d 128, 2D 8x8, swept with `APRILTAG_VK_WG`, auto choice within noise | done |
| Subgroups | min = max = 16 (vulkaninfo), no size control to gain; ballot/shuffle variants measured 6.6x slower on this GPU | rejected, keep |
| FP16 / packed int8 dot product | pipeline is integer; `VK_KHR_shader_integer_dot_product` (4x8-bit packed accelerated) exists but nothing here is a dot product of byte vectors; fp16 coordinates break exactness (PERFORMANCE.md 6b) | reject |
| FMA/CVT/SFU throughput | the only float work: `scatter_index_points.comp:53-61` (pseudo-angle, one divide) and the `sqrt` for `W` in `sort_points_local_body.glsl:46`, once per point; `sort` is 0.99x DRAM-insensitive and barrier-bound, not ALU-bound | not a limiter |
| Specialization constants for `width`/`height` (BP-7) | still push constants in `uf_merge`, `uf_init`, `label_pixels`, `blob_diff` | small; check malioc instruction counts first (finding 5) |
| Register pressure (32-register occupancy cliff) | unknown; shaders are short, probably under 32 | malioc (finding 5) |
| Atomics | see finding 4 | measure |

**New idea: rank-by-counting for small blobs, using Valhall's single-cycle uniform loads.** The `sort`
span on Mali is barrier/latency-bound (0.99x DRAM sensitivity; the comparator-enumeration change that
won 27-49% on RDNA was neutral here, OPTIMIZATION_NOTES item 15). The odd-even network needs
`log2(cap) * (log2(cap) + 1) / 2` barriers per blob: 21 at cap 64, 28 at 128, 36 at 256. An
alternative with two barriers: after loading the packed keys into shared memory, each thread computes
its key's rank as the count of smaller keys (`s_packed` words are unique because the low 12 bits are
the local index, so the rank is the exact sorted position and the output is bit-identical to the
network's). In that loop every lane of a warp reads the **same** shared word, which on Valhall is one
cache line returned in one cycle (research/07, Valhall shader core guide), and reading it as `uvec4`
quarters the issue count. Cost is O(n^2 / 4) loads per blob spread over its warps, so it only wins for
small blobs: a rough issue count (n = 64: 4 warps x 16 `uvec4` loads ~ 64 LS cycles vs 21 barriers) says
it is clearly cheaper there, around break-even near n = 128-256, and loses above. Two pipeline variants
(or a uniform branch on `count`, since `count` is workgroup-uniform) keep the network for large blobs.
- **Expected gain:** unknown; it depends on the blob-size histogram (summary A4, still unmeasured) and on
  what a Mali barrier really costs inside a 256-thread workgroup. Ceiling = the share of the `sort` span
  (~10% of the GPU phase) spent in small blobs' barrier rounds. Estimate 0-5% of GPU time.
- **Cost and risk:** ~30 lines in one shader; exact by construction (unique keys).
- **Prior art:** research/05 idea 7 suggested rank-by-counting for count <= 32 only, as a sub-case of
  blob binning, without the uniform-load argument; never built. The barrier-removal ceiling for the
  sort was measured on MX230/Intel (5-9%) but **never on Mali** (research/05 idea 6).
- **Verdict:** **measure first:** (1) dump the per-blob point-count histogram on the corpus (the
  `selected` extents are already read back on the host); (2) on the Pi, time a deliberately incorrect
  build that removes all of the sort's barriers (the tree's A9 method) to get the Mali ceiling. Build
  only if the ceiling is > ~20% of the `sort` span and most blobs are under ~128 points.

### 11. NEON and compiler flags for the CPU tail (RK3588 CPU)

- **Idea:** tune the CPU tail for the A76 (NEON, `-mcpu`).
- **Facts:** `CMakeLists.txt` sets only `CMAKE_BUILD_TYPE Release` (`-O3`); there is no `-mcpu` /
  `-mtune` / `-march` anywhere, so the Pi build targets generic armv8-a. NEON (ASIMD) is in the aarch64
  baseline, so GCC 14's `-O3` already auto-vectorises where it can, and GCC's default outline atomics
  pick LSE at run time (the WorkerPool's atomic counter is fine). All eight RK3588 cores are
  Armv8.2-A, so `-mcpu=cortex-a76.cortex-a55` would be safe on this SoC but not in the generic arm64
  `.deb` (the release workflow builds arm64 for any board).
- **Why the gain is small:** PERFORMANCE.md section 4 measured the refine loop as memory-latency bound
  ("eight scattered byte loads per step"), where neither wider SIMD nor scheduling helps, and `exact`
  is double precision (2 lanes per NEON register) with upstream's operation order, which forbids FMA
  contraction and reassociation if output must stay identical. `quad_decode` is per-blob scalar control
  flow (DP corner seeding, peak detection). The large tail lever is not refining quads that never decode
  (96.8% of refine time, PERFORMANCE.md 8e), which is device-agnostic and outside this file, and running
  the tail on A76s at full clock (finding 3), which is worth far more than codegen.
- **Expected gain:** estimate 0-5% of the tail from `-mtune=cortex-a76` (scheduling only, keeps the
  baseline ISA); hand NEON for the refine kernel: little, for the reasons above.
- **Verdict:** **low priority.** If tried: a Pi-only build with `-mtune=cortex-a76` (no ISA change, so
  output is identical) A/B'd on `quad_decode` + `tag_decode` with governors pinned and `taskset -c 4-7`;
  keep only if > 3%.

### 12. Queue-level options on libmali: priority, core partitioning, second queue, driver version (Mali)

- **Global priority** (`VK_EXT/KHR_global_priority`, LOW..REALTIME offered on the one family): useful
  only if something else uses the GPU at the same time; the product's `Server` was not using the GPU
  when sampled. A `ContextOptions` knob requesting HIGH is cheap insurance against a desktop compositor
  or another GPU client delaying a frame; no gain when the detector is alone. **Optional, low.**
- **`VK_ARM_scheduling_controls` rev 1** (per-queue shader-core count): can only split the 4 cores
  between queues; it cannot add throughput, and 8c showed a queue per stream is already slightly worse
  than one shared queue on this GPU. **Reject.**
- **Second queue / more frames in flight:** measured (PERFORMANCE.md 8b/8c/8g): one stream ~381 fps,
  two or more ~445 fps, so a single pipelined stream leaves ~15% of the GPU idle (per-frame host
  overhead and fence round trip). For one high-fps camera the recipe is two `GpuDetector`s on the same
  queue taking alternate frames, which is what the 2-stream benchmark already measures: ~+16%
  throughput at +1 frame of latency. Every realistic camera rate (<= 120 fps) is far below 381 fps, so
  this matters only for multi-camera rigs, where it already happens. **No new work.**
- **Driver version:** the board has only `libmali-valhall-g610-g24p0` 1.9-1; the g24p0 vs g29p1 A/B
  (summary C4) and research/07's `CMAR_OPTIMIZE_FOR_LATENCY=1` environment probe are still untested and
  are 10-minute experiments once g29p1 is installed. PanVK is not an option on this image (the
  `gpu-panthor` node is disabled; PhotonVision measured it ~13x slower on Mesa 25.0). **Measure first,
  low expected gain.**
