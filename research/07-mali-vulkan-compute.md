### BP-1: Workgroup size and barriers (BP 3.4 s9.2) — Arm, Arm GPU Best Practices Developer Guide 101897 v3.4 (Issue 10, 2025)
- URL: https://developer.arm.com/documentation/101897/latest (cached text: claude-research/mali/bp34.txt, s9.2 lines ~4546-4608)
- Technique: Valhall splits a fixed register file across a variable number of threads. "The GPU hardware can split up, and then merge, workgroups during shader core resource scheduling. If barriers or shared memory are used, then GPUs cannot do this" - the whole workgroup must be co-resident, which limits registers per thread and can force stack spills. Rules: 64 as baseline; multiple of 4; "Do not use more than 64 threads per workgroup"; try smaller first when using barriers/shared; square 8x8 for 2D image work; split per-workgroup setup/reduction into separate passes rather than barriers; "Do not assume that barriers with small workgroups are free". Subgroup size is 16 or smaller - do not rely on wider warps to skip barriers.
- Reported speed-up: no numbers in the guide.
- Accuracy / determinism impact: none (scheduling only).
- Applicability to vkapriltag: Mali picks wg1d=128, wg2d=8x8 (PERFORMANCE.md s1), and `APRILTAG_VK_WG` sweep found 128 within noise of best - consistent with the guide for barrier-free shaders (for those the hardware can split/merge freely, so size matters little). Where the rule bites is shaders that DO use barriers/shared: (a) `uf_merge_body.glsl` - the largest span - has `shared uint wg_changed` + two `barrier()`s per 256-wide (spec-constant) workgroup purely to aggregate the convergence flag; that forbids workgroup split/merge on exactly the latency-bound, dependent-load shader where more schedulable threads help most, and forbids early exit (comment: "every invocation must reach both barriers"). Replacing it with `if (merged && changed_flag == 0u) atomicOr(changed_flag, 1u);` (read-before-atomic, same trick as extents; merges are rare so the atomic is rare) removes the shared variable and both barriers, and is bit-identical (flag is only tested for zero/non-zero). Not in any rejected list - the rejected "subgroup aggregation" is a different thing. (b) `scan_block.comp` runs at scan_wg=1024 on Mali with `shared temp[1024]` and barriers - 16x the guide's ceiling; small span, low priority. (c) `sort_points_local` 256 threads + shared + barriers was measured best at 256 (64: 5.71 ms, 256: 3.08 ms, OPTIMIZATION_NOTES s5) - measured beats rule; leave.

### BP-2: Shared memory on Arm GPUs (BP 3.4 s9.3) — Arm, 2025
- URL: as BP-1 (bp34.txt lines ~4609-4680)
- Technique: "Arm GPUs do not implement dedicated on-chip shared memory for compute shaders. The shared memory that is available to use is system RAM that is backed up by the load-store cache." Use shared only to share significant computation; keep it small (reduces L1 thrash); reduce precision/width; "It can be computationally cheaper splitting an algorithm over multiple shaders when compared to inserting barriers"; "For barriers, smaller workgroups are less expensive"; "Do not copy data from global memory to shared memory on Arm GPUs. Doing so pollutes the caches"; do not use the "thread 0 setup / barrier / work / barrier / thread 0 reduce" pattern - split into three shaders.
- Reported speed-up: none quoted.
- Accuracy / determinism impact: none.
- Applicability to vkapriltag: Confirms in-tree rejections (tile-local UF, preprocessing fusion) - both paid for DRAM traffic with shared traffic + barriers. Note the guide says the backing is the *load-store cache* (L1), with RAM behind it, which is slightly different from the tree's wording "backed by L2". `uf_merge`'s wg_changed pattern is literally the "thread 0 setup / barrier / work / barrier / thread 0 push" anti-pattern the guide names (see BP-1 idea). `sort_points_local` copies global->shared (the guide's other anti-pattern) but a sort needs a scratch buffer and the kernel is already measured; a register-resident alternative (each thread sorts a few keys in registers + subgroup shuffles) is ruled out by the Mali subgroup results.
- Verification: [verified from primary source]

### BP-3: Atomics (BP 3.4 s10.13) — Arm, 2025
- URL: as BP-1 (bp34.txt "10.13 Atomics")
- Technique: "The key performance problem with atomics is contention. Atomic operations from different shader cores hitting the same cache line requires data coherency snooping through L2 cache, which is computationally expensive." "Atomics are efficient when a shader core controls the necessary cache line in its L1." Rules: design out contention; "Consider spacing atomics 64 bytes apart to avoid multiple atomics contending on the same cache line"; accumulate into a shared-memory atomic and push one global atomic per workgroup; for OpenCL use `cl_arm_get_core_id` for explicit per-shader-core atomic variables; prefer multi-pass designs over atomics where available. Counters exist for L1 snoops from other cores.
- Reported speed-up: none quoted.
- Accuracy / determinism impact: none if the reduction is associative (integer min/max/add are).
- Applicability to vkapriltag: The extents reduction is the second-largest Mali span and is atomic-bound (1.01x DMC sensitivity). Two concrete, untried ideas follow directly: (1) **Per-core privatization instead of per-workgroup**: today copy = `gl_WorkGroupID.x & 7`, so each of the 8 copies is hit by workgroups scheduled on all 4 cores of the G610 MP4 -> every copy's lines still bounce between L1s via L2 snoops. `VK_ARM_shader_core_builtins` (present in libmali g24p0 and g29p1 extension lists in cache; absent in g6p0) exposes `gl_CoreIDARM` / `gl_CoreCountARM`, the Vulkan analogue of the `cl_arm_get_core_id` the guide recommends; copy = core id makes each copy L1-resident on one core. Could also be combined: copy = coreID*2 + (wg&1). (2) **Pad `MinMaxExtentsGpu` from 32 to 64 bytes** (it is 8 x int32 = 32 B, so two different blobs share every 64-byte line and contend falsely); padding the privatized region only costs 4096 x 8 x 32 B = 1 MiB extra. Both bit-identical. Same reasoning applies to `hash_group`'s CAS table (4-byte slots, 16 per line - but linear probing wants locality, so leave it) and the `blob_diff` append counter (one address, ~65k appends/frame at decimation 2; the tree rejected *subgroup* aggregation of it and never takes subgroup paths on Mali, but the guide's *shared-memory* per-workgroup aggregation has not been measured there - though it would add exactly the barriers BP-1 warns about, so bound it first by a deliberately-wrong build that appends to per-workgroup private counters). Bound cheaply: the plain-store bound (0.434 -> 0.062 ms) says atomics cost ~0.37 ms of which privatization recovered part; a quick A/B of K-copy-by-coreID vs K-by-workgroup is one shader line plus an extension check.
- Verification: [verified from primary source] for the guide; `gl_CoreIDARM` availability from cached libmali extension lists [verified from cached driver strings], not run.

### BP-4: Vulkan pipelining, barriers, queries, timestamps (BP 3.4 s3.8, s3.9, s3.12, s10.5) — Arm, 2025
- URL: as BP-1 (bp34.txt lines ~1156-1430, 1534-1575, "Beware timestamp effects" in s10.5)
- Technique: Mali has two independently scheduled hardware slots: vertex/compute (COMPUTE_SHADER, TRANSFER for buffer-to-buffer, DRAW_INDIRECT) and fragment. Rules: set srcStageMask as early and dstStageMask as late as possible; never BOTTOM_OF_PIPE->TOP_OF_PIPE or ALL_COMMANDS->ALL_COMMANDS; "Do not use more barriers than needed. Each barrier comes with some processing cost"; "Only use intra-queue barriers when they are needed and put as much work as possible between barriers"; "Zero-copy algorithms are the most efficient, so minimize the use of TRANSFER copy operations"; read back with fences, never vkQueueWaitIdle/vkDeviceWaitIdle; do not VkEvent-signal-then-wait; no semaphores within one queue. Buffer-to-buffer transfers run in the compute slot. Queries: only read when known available. Timestamps "have an overhead" and "can impact work scheduling and introduce serialization".
- Reported speed-up: none quoted.
- Accuracy / determinism impact: none.
- Applicability to vkapriltag: Already compliant: `ComputePipeline::Barrier` issues one global `VkMemoryBarrier` COMPUTE->COMPUTE (+TRANSFER only where needed); fences, not WaitIdle (`Context::SubmitAndWait`); one submission per frame on unified memory (PERFORMANCE.md 3c). The in-tree finding that timestamps cost ~9% of GPU total on Mali (3.16 vs 2.90 ms) is exactly the guide's warning - per-span numbers are for attribution only. Remaining lever here: barrier *count*. Mali barrier cost scales with in-flight work (2.6-18.7 us, PERFORMANCE.md s3) and the frame has ~31 barriers, so the upper bound is roughly 0.1-0.5 ms. "Put as much work as possible between barriers" argues for (a) auditing which of the ~31 are true RAW/WAR dependencies and turning the rest into `BarrierKind::None` (e.g. independent `clear` fills vs early passes, `init_extents` vs the labelling chain), and (b) reordering independent dispatches so two share one barrier. Bound: a deliberately-wrong build with all barriers dropped (the tree's A9 method) on Mali, reading GPU total on a still image - the ceiling in one build.

### BP-5: CPU-side Vulkan overheads - pipelines, memory types, command buffers, descriptors (BP 3.4 s4.2-4.9) — Arm, 2025
- URL: as BP-1 (bp34.txt lines ~1607-2115)
- Technique: Serialize a VkPipelineCache to disk (Arm ignores DERIVATIVE and DISABLE_OPTIMIZATION flags). Do not use vkAllocateMemory as a general allocator (it is a kernel call). Memory types on Bifrost+: (1) DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT - uncached, write-combined, best for CPU write-only (memcpy / sequential writes); (2) +HOST_CACHED, incoherent - needs vkFlush/vkInvalidateMappedMemoryRanges, "both calls are expensive to use, so must be used sparingly"; (3) COHERENT|CACHED - only "if the chipset supports the hardware coherency protocol"; (4) LAZILY_ALLOCATED. Never read uncached memory on the CPU; map persistently. Command buffers: ONE_TIME_SUBMIT is best; "If the alternative is to replay the same command sequence every time in application logic, then use SIMULTANEOUS_USE_BIT ... more efficient than an application replaying commands manually"; avoid pools with RESET_COMMAND_BUFFER_BIT and high-frequency vkResetCommandBuffer, prefer vkResetCommandPool; TRANSIENT_BIT and vkTrimCommandPool are ignored. Descriptors: allocate up front, pack bindings with no holes; push constants equal UBOs on Arm.
- Reported speed-up: none quoted.
- Accuracy / determinism impact: none.
- Applicability to vkapriltag: The RK3588 libmali (g6p0 vulkaninfo pastebins in cache, `pb_35H2dvsR.txt` / `pb_NYD1z027.txt`) exposes only types 0x7 (coherent), 0xb (cached, incoherent) and LAZILY - **no coherent+cached type**, i.e. the RK3588 integration lacks the CPU/GPU coherency the guide mentions. Every in-place readback of `line_fit_points_buf_` / `selected_extents_buf_` therefore needs `vkInvalidateMappedMemoryRanges` (Buffer.cpp does this). Worth a micro-measure: the invalidate is a cache-maintenance walk over the range, so invalidating only the `num_points * 8` bytes actually written rather than the whole buffer may matter at 1080p (check Buffer.cpp's range argument). Pipeline cache: done. Command buffers: the tree uses a pool with RESET_COMMAND_BUFFER_BIT, per-frame vkResetCommandBuffer and ONE_TIME_SUBMIT, and **re-records ~35 dispatches and ~31 barriers every frame**. The fused frame's command stream no longer depends on host-side counts (indirect dispatch, `count_from_buffer`), so it could be recorded once per configuration and resubmitted (no flag needed while it is never pending twice). With one submission per frame the GPU idles while the CPU records, so record time is pure latency. Bound: read `last_profile_.cpu_begin_ms` plus the record span on the Pi (probably tens of us). Descriptors: allocated once per pipeline - compliant.
- Verification: [verified from primary source] for the guide; memory types [verified from cached vulkaninfo, driver g6p0-01eac0]; later libmali versions not checked for a coherent type.

### BP-6: Precision and FP16 (BP 3.4 s10.1-10.2) — Arm, 2025
- URL: as BP-1 (bp34.txt "10.1 Minimize precision")
- Technique: Full FP16 register-file and ALU support; "highp can use up to twice the resources and halve the speed"; use f16vec2/f16vec4 - "Scalar float16_t does not gain the same benefit"; avoid frequent FP16<->FP32 casts; lowp == mediump on Arm. VK_KHR_shader_float16_int8 for arithmetic, VK_KHR_16bit_storage for storage.
- Reported speed-up: "up to 2x", qualitative only.
- Accuracy / determinism impact: large - FP16 has an 11-bit mantissa.
- Applicability to vkapriltag: Almost nothing applies. The GPU pipeline is integer end to end (thresholds, union-find indices, atomics, packed line-fit records); the only float math on the GPU is the theta key / gradient weight in `sort_points_local`, which must stay bit-identical. fp16 coordinates are already rejected in-tree (PERFORMANCE.md 6b: x2 reaches 3839). The guide offers no 16-bit *integer* ALU speed-up; int16 packing would be a storage play only, capped by the 15% bandwidth share. Rejected.
- Verification: [verified from primary source]

### BP-7: Shader code - vector memory access, branches, uniforms/specialization, instruction cache (BP 3.4 s10.3-10.11) — Arm, 2025
- URL: as BP-1 (bp34.txt lines ~4800-5100)
- Technique: Bifrost/Valhall arithmetic is scalar per thread and warp-based, but they "still implement vector access to memory": use vector loads per thread, and make the threads of a quad (Valhall: a warp of 16) access "overlapping or sequential memory ranges ... to allow load merging". Uniforms/push constants (<=128 bytes) are promoted to registers; "Vulkan push constants are equal to UBOs"; control flow parameterized by uniforms should be specialization constants ("allows the compilation to completely remove unused code blocks and statically unroll loops"). Minimize divergence among spatially adjacent threads; use min/max/clamp/mix for small branches. Instruction cache: shorter shaders with many threads; don't over-unroll; don't duplicate identical pipelines. Use built-ins; "Do not do clears or fills of buffers with shader code where vkCmdFillBuffer can be used".
- Reported speed-up: none quoted.
- Accuracy / determinism impact: none.
- Applicability to vkapriltag: Vectorization was tried and lost on Mali (+6%/+11%, item 9). That fits the guide's point that load merging already happens across the 16-wide warp when adjacent lanes read adjacent addresses, which the one-row-tall `uf_merge` and raster `blob_diff` already do. **Specialization constants**: `width`/`height` are push constants in `uf_merge`, `uf_init`, `label_pixels`, `blob_diff` etc., but they are fixed per `GpuDetector`. As spec constants they would let the compiler fold `y*width`, make bounds checks constant, and resolve the `count_from_buffer` / `honour_changed_flag` branches (per-dispatch-site constants, so 2 pipeline variants per shader). Division by a constant also becomes mul+shift, which removes the runtime-divide concern that forced `uf_merge` to 2D. Expected uplift is small (a few instructions per thread in latency-bound shaders); bound it with malioc instruction counts before measuring. `init_extents.comp` writes non-zero sentinels (min = INT_MAX etc.), so vkCmdFillBuffer can't replace it directly without reordering the struct - minor.
- Verification: [verified from primary source]; the spec-constant idea is my inference.

### BP-8: Image vs buffer, texture unit, robustness, staging (BP 3.4 s8.2-8.4, s9.1) — Arm, 2025
- URL: as BP-1 (bp34.txt lines ~3613-3800, 4426-4545)
- Technique: For read-only data use `texture()`/`texelFetch()` rather than `imageLoad()`: "texture() operations use the texture unit and both imageLoad() and imageStore() use the load or store unit. The load/store units are often already being used in compute shaders for generic memory accesses" - texel fetches load-balance onto a separate pipe. imageStore: four adjacent lanes should hit the same 64-byte line; compute threads pack linearly X then Y. The texture unit is full rate for nearest/bilinear, and **on Valhall "YUV has a 1x cost, irrespective of the plane count"**. robustBufferAccess costs measurable performance on UBO and SSBO access - disable in release. Avoid staging buffers except for tiled-optimal images; VK_EXT_host_image_copy (driver r50+) avoids staging using HOST_CACHED memory.
- Reported speed-up: none quoted.
- Accuracy / determinism impact: texelFetch is exact (no filtering); none.
- Applicability to vkapriltag: robustBufferAccess is not enabled (zero optional features) - compliant. The in-tree rejection of the tiled image / texelFetch (A7) was decided on Intel Iris + MX230 data (A11's W precompute), never measured on Mali, and argued from the *layout* (tiling) benefit only. The guide's argument is different: **issue-port offload** from the load/store unit to the texture unit, which matters on a part where labelling, sort and extents are load/store-latency or atomic bound. The cheapest place to test it is the **input**, not the decimated image: `decimate` reads the camera frame, and if the frame arrives as a dma-buf (see the camera entries) it can be imported as a VkImage (R8 luma plane, linear or DRM-modifier tiled) and read with `texelFetch` - zero-copy and LS-offloaded at once. `sort_points_local`'s four gradient taps could also use texelFetch through an R8_UINT uniform texel buffer view of the existing buffer (no copy, no layout change), but A11 put those taps at 2-3% of `sort`, so this is small. Low priority except as part of the camera zero-copy path.

### Mali-G610 Performance Counters Reference Guide 1.8 (102812_0108) — Arm, 2024
- URL: https://documentation-service.arm.com/static/667167b8d72aaf32efecec66 (cached: claude-research/mali/web/g610_counters_18.pdf/.txt)
- Technique: Counter definitions for the exact target GPU. Most relevant for vkapriltag: (a) **"All registers warp percentage"** - "percentage of warps that use more than 32 registers, requiring the full register allocation of 64 registers. Warps that require more than 32 registers halve the peak thread occupancy of the shader core, and can make shader performance more sensitive to cache misses and memory stalls" ($MaliShaderWarpsAllRegisterWarps). (b) LS unit issue split: full vs partial read/write issues and **$MaliLoadStoreUnitCyclesAtomicAccess** - "Atomic memory accesses are typically multicycle operations per thread in the warp, so they are exceptionally expensive." Partial-width accesses waste the LS path; fix by "adjacent threads in a warp access adjacent addresses". (c) LS bytes read from L2 / from external memory per access (L1 and L2 effectiveness). (d) Warp divergence %, full-warp % ("Compute dispatches use work groups that are a multiple of warp size", warp = 16). (e) G610 has a CSF with three hardware queues (compute, vertex, fragment); "Compute queue utilization" counter.
- Reported speed-up: n/a (reference).
- Accuracy / determinism impact: n/a.
- Applicability to vkapriltag: PERFORMANCE.md s9 says "Mali exposes no external GPU profiler at all" - that is not right for this GPU: these counters are exactly what the tree has been inferring from DMC-clock sweeps and deliberately-wrong builds. The single most actionable check: are any of the latency-bound shaders (`uf_merge` with its `find()` loops, `blob_diff`, `sort_points_local`, `reduce_extents_hash_atomic64` with 64-bit values) above 32 work registers? If so they run at half occupancy, which directly hurts a dependent-load-latency-bound kernel, and trimming them under 32 is the Valhall-specific lever that the vectorization attempts (which *raise* register count - a plausible reason for their +6%/+11% loss) moved in the wrong direction. The LS atomic-issue counter directly measures extents/hash_group/blob_diff atomic cost, and "LS bytes read from L2 per access" separates L1-miss from DRAM-miss for labelling.
- Verification: [verified from primary source]

### azhirnov/cpu-gpu-arch "ARM-Mali-Valhall.md" — Andrey Zhirnov, GitHub (compiles Arm docs + gpuinfo), accessed 2026-09

### Mali Offline Compiler (malioc) - static register / spill / cycle stats — Arm (Performance Studio), user guide 101863 + Arm forum thread 52294

- Reported speed-up: n/a (tool).

### libGPUCounters (formerly HWCPipe) 2.x — Arm, GitHub ARM-software/libGPUCounters
- URL: https://github.com/ARM-software/libGPUCounters (tree listing and product_id.hpp fetched via GitHub API)
- Technique: Library that samples the same Mali hardware counters Streamline shows, from inside the application, through the kbase kernel driver ioctls (`backend/device/src/device/ioctl/kbase`, plus `kbase_pre_r21`). README: "aims to support all Arm GPU products from the Mali-G71 series or later" and "This library only supports devices using the Arm commercial driver." `product_id.hpp` lists `g610` in the Valhall family and has a `csf` backend type; the repo ships `docs/mali-g610_counter_reference.html` and a machine-readable counter spec.
- Reported speed-up: n/a.
- Accuracy / determinism impact: none (sampling only; small overhead).

### Production MPP -> Mali zero-copy: Jellyfin RKMPP docs + FFmpeg `opencl_map_from_drm_arm` — Jellyfin team; FFmpeg libavutil/hwcontext_opencl.c (master), accessed 2026-09
- URL: https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/rockchip/ ; https://github.com/FFmpeg/FFmpeg/blob/master/libavutil/hwcontext_opencl.c (cached mali/web/cam/ffmpeg_hwcontext_opencl.c, lines 2683-2820)
- Technique: Jellyfin ships a "zero-copy transcoding pipeline" on RK3588 of MPP decode -> RGA -> **Mali-G610 OpenCL** (HDR tone mapping) -> MPP encode. It requires the BSP 6.1/5.10 kernel and libmali (e.g. "v1.9-1-2131373"), and its logs show "cl_arm_import_memory found as platform extension" and "DRM to OpenCL mapping on ARM function found (clImportMemoryARM)". The FFmpeg code imports each DRM-PRIME object fd **as a plain buffer** with `clImportMemoryARM(ctx, flags, {CL_IMPORT_TYPE_ARM, CL_IMPORT_TYPE_DMA_BUF_ARM, 0}, &fd, size)`. It then carves each plane out with `clCreateSubBuffer(region.origin = plane->offset, size = pitch*height)` and wraps that sub-buffer as an image. It warns that nonzero format modifiers (i.e. AFBC / tiled) "may not be as expected", so only linear NV12 is supported.
- Reported speed-up: "RK3588/3588S supports up to 1080p@480fps or 4k@120fps transcoding" (whole pipeline, marketing-level; no GPU-side split).
- Accuracy / determinism impact: none. The GPU reads exactly the decoder's bytes.
- Applicability to vkapriltag: This is the existence proof that the MPP-dma-buf -> libmali-GPU import path works in production on this exact SoC and driver family, and it gives the recipe. The Vulkan equivalent needs no image at all, because `decimate` already reads a storage buffer (`gray_buf_`). (1) Create the VkBuffer with `VkExternalMemoryBufferCreateInfo{DMA_BUF_BIT_EXT}`. (2) Allocate with `VkImportMemoryFdInfoKHR{fd}`, taking memoryTypeBits from `vkGetMemoryFdPropertiesKHR`. (3) Bind the Y-plane descriptor at `plane[0].offset`, which must be a multiple of `minStorageBufferOffsetAlignment`, else pass the offset as a push constant. (4) Pass the plane pitch as the row stride. Pool about 4 imported buffers keyed by fd, since MPP recycles a small buffer ring, so the import cost is paid once. This removes the ~0.22 ms CPU memcpy into `gray_buf_` (OPTIMIZATION_NOTES upload row) and, more importantly, lets the whole camera->detector path skip the CPU. A new API entry point is needed: `Detect(int dmabuf_fd, offset, pitch)` beside `Detect(const uint8_t*)`. Check `vkGetPhysicalDeviceExternalBufferProperties` on g24p0 for DMA_BUF import of STORAGE buffers before building. Only Jellyfin's OpenCL path is proven, not Vulkan buffer import. Mali/RK3588 only; on RDNA the same code works for V4L2/VA-API dma-bufs but gains little.

### V4L2 buffer sharing on the two camera paths: uvcvideo (vb2-vmalloc) vs Rockchip rkisp v30 (vb2-dma-sg/contig) — Linux master `drivers/media/usb/uvc/uvc_queue.c`, `videobuf2-vmalloc.c`; rockchip-linux/kernel develop-6.1 `drivers/media/platform/rockchip/isp/capture_v30.c`, accessed 2026-09

- Technique: **USB (UVC) cameras**, which is what PhotonVision normally uses on an Orange Pi 5, set `io_modes = VB2_MMAP | VB2_USERPTR | VB2_DMABUF` with `mem_ops = &vb2_vmalloc_memops`. The driver CPU-copies every URB payload into a vmalloc buffer. That buffer can be exported (VIDIOC_EXPBUF, `vb2_vmalloc_get_dmabuf`), but the exporter's `map_dma_buf` "return[s] previously mapped sg table" after the first map, and it implements **no `begin_cpu_access`/`end_cpu_access`**. So after the first frame, nothing cleans the CPU caches for a non-coherent importer. **MIPI-CSI cameras through the RK3588 ISP** (rkisp v30) use `hw_dev->mem_ops`, i.e. vb2-dma-sg or vb2-dma-contig (`is_dma_sg_ops` / `is_dma_contig`), with the same MMAP/USERPTR/DMABUF modes. The ISP DMA-writes NV12 directly, and those allocators do proper per-buffer sync.
- Reported speed-up: n/a (mechanism).
- Accuracy / determinism impact: **UVC EXPBUF -> Mali import risks stale cache lines**. The RK3588 GPU is IO-non-coherent (no coherent+cached memory type, BP-5), and uvcvideo writes the frame through cached kernel mappings. That would be a nondeterministic corruption, which the bit-identity gate compares against the same corrupted input and so would *not* catch.
- Applicability to vkapriltag: (1) **UVC + YUYV**: exporting the UVC buffer into Vulkan saves only the ~0.22 ms user-space memcpy, because the kernel already copied the data once. It adds the coherency hazard above. Not worth it, so keep the memcpy into `gray_buf_`, but fold the YUYV->Y de-interleave into that same copy or into `decimate`. (2) **UVC + MJPEG**, the common high-fps mode: the bytes are compressed, so the path is MJPEG bitstream (a small memcpy) -> MPP decode into a dma-buf pool -> Vulkan import (previous entry). This is the zero-copy that matters. (3) **CSI camera via rkisp**: the ISP writes NV12 straight into a dma-buf with correct sync. That dma-buf can go directly into vkapriltag (Y plane = offset 0), so camera to detector never touches the CPU. It is the cleanest path, but PhotonVision on the Orange Pi mostly uses USB cameras, and rkisp needs the BSP kernel plus a tuned IQ file per sensor. Mali/RK3588 only.

Load/store: "Data that is stored in a single 64-byte cache line per clock cycle can be accessed ... data can be returned in a single cycle if all threads access data inside the same cache line"; "The load/store unit includes 16KB L1 data cache per core, which is backed up by the shared L2 cache". - Reported speed-up: n/a.
- Accuracy / determinism impact: n/a.
- Applicability to vkapriltag: (1) Confirms the 32-register occupancy cliff (see malioc / counters entries) and 16 KB L1 per core from Arm itself. The guide is Valhall Gen1 (G77), but the counter guide for G610 describes the same register rule. (2) **Working-set arithmetic at 1280x800 decimation 2 (640x400 = 256k pixels):** `parent_buf_` is 4 B/px = 1.0 MB and `thresholded_buf_` 256 KB, so the union-find working set alone is ~1.25 MB against a 1 MB L2 shared with everything else. Labelling's dependent `find()` loads therefore miss L2 part of the time, not just L1, and the "decimated image lives in L2" statement in OPTIMIZATION_NOTES holds for the 256 KB image but not for the parent array. That doesn't contradict the 1.01x-ish DMC sensitivity: DRAM *latency* at a random miss is the cost, not bandwidth. It predicts labelling cost grows super-linearly once resolution pushes `parent` well past 1 MB (1600x1200 d2 = 1.9 MB). ### Arm-authored Vulkan performance samples: command_buffer_usage, pipeline_barriers, async_compute — Arm / Khronos Vulkan-Samples (main), accessed 2026-09; libmali queue layout from cached vulkaninfo
- URL: https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/{command_buffer_usage,pipeline_barriers,async_compute} (cached mali/web/vks/); claude-research/mali/pb_35H2dvsR.txt line 546
- Technique: (a) Command buffers, measured on Mali/Android: request+reset time was 53.3 ms with pool reset (0.45% of the capture), 140.29 ms with individual `vkResetCommandBuffer` (1.16%), and 3319 ms with allocate/free (28.8%). "Performance may be reduced if the SIMULTANEOUS_USE_BIT flag is set". (b) Barriers: "Mali GPUs queue their work in a pair of internal slots, one for vertex/compute workloads and one for fragment"; replacing BOTTOM->TOP barriers with tight stage masks removed pipeline bubbles for a **13% frame-time** improvement; "use Streamline ... You can quickly see if there are bubbles in scheduling". (c) Async compute: "At least on Arm Mali GPUs, compute workloads run in the same queue as vertex shading"; multiple VkQueues let independent work overlap, with queue priorities as the control. libmali on RK3588 (g6p0 vulkaninfo) exposes **one queue family with `queueCount = 2`** (GRAPHICS|COMPUTE|TRANSFER). On the CSF-based G610 each queue can map to its own firmware command stream.
- Reported speed-up: 13% (barrier stage masks, graphics sample); the command-buffer table above.
- Accuracy / determinism impact: none within a frame. Cross-frame overlap needs double-buffered per-frame state, which is deterministic per frame.
- Applicability to vkapriltag: (1) The tree uses a RESET_COMMAND_BUFFER_BIT pool with per-frame `vkResetCommandBuffer`. The sample shows pool reset is about 2.6x cheaper for that operation, and at 1 buffer/frame the absolute saving is microseconds. Take it only as part of the replay change (BP-5). (2) Barriers are already COMPUTE->COMPUTE, so the 13% case doesn't apply. (3) **New idea: GPU-side overlap of consecutive frames on the second queue.** Each of the ~31 in-frame barriers drains the compute slot (2.6-18.7 us, growing with in-flight work), and the latency-bound tail stages (extents, sort with small per-blob workgroups) likely leave cores idle. Submitting frame N+1's front half (decimate..labelling) on queue 1 while frame N's back half (extents..sort) runs on queue 0 would let the CSF fill those bubbles. That raises throughput, but not single-frame latency. It is different from the rejected CPU-tail pipelining, which was CPU/GPU DRAM contention. **Cheap bound, no code change:** run two `apriltag_vulkan_validate --loop` processes at once on the Pi. If aggregate frames/s exceeds 1.0x the single-process rate by a clear margin, the bubbles are real and fillable; if it is about 1.0x, the GPU is saturated and the idea is dead. Mali mainly; RDNA has async compute queues too, but its span is 0.66 ms.

### VK_ARM_shader_core_builtins / GLSL_ARM_shader_core_builtins specs — Arm (Kevin Petit, Jan-Harald Fredriksen), rev 2, 2022-10
- URL: https://github.com/KhronosGroup/Vulkan-Docs/blob/main/appendices/VK_ARM_shader_core_builtins.adoc ; https://github.com/KhronosGroup/GLSL/blob/main/extensions/arm/GLSL_ARM_shader_core_builtins.txt (cached mali/web/ext/)

## Conclusions

Ranked for the Orange Pi 5 / Mali-G610 MP4 on libmali, unless marked otherwise. "Bit-identical" means the idea can't change the output. 28 entries above.

### A. End to end: the biggest wins sit outside the GPU phase

1. **Camera zero-copy with hardware MJPEG decode (BSP kernel only).**
   - *Why:* PhotonVision's own numbers (50 ms GPU vs 60 ms CPU end to end at 1600x1200 d1) and #1497 put software MJPEG decode, not the detector, on the critical path.
   - *Recipe:* UVC MJPEG bitstream -> MPP `mjpeg_rkmpp` (560 Mpx/s spec, about 1.8 ms of decoder time at 1280x800) -> NV12 dma-buf pool -> import each fd once as a Vulkan **storage buffer** (`VkExternalMemoryBufferCreateInfo` + `VkImportMemoryFdInfoKHR`, DMA_BUF handle type; present in g24p0/g29p1/PanVK) -> `decimate` reads the Y plane at `offset`/`pitch`. Needs a new `Detect(fd, offset, pitch)` entry point.
   - *Proof of path:* Jellyfin's MPP -> Mali OpenCL (`clImportMemoryARM` + a sub-buffer per plane) already works in production on this SoC.
   - *Reverse direction:* libmali allocates host-visible memory from `/dev/dma_heap/system-uncached`, so exporting `gray_buf_` to MPP ("pure external" mode) is the other way round.
   - *Uplift:* several ms of A76 decode per frame plus the 0.22 ms upload.
   - *Risk:* the hardware IDCT may differ from libjpeg-turbo, but the GPU-vs-CPU gate is unaffected. Integration and maintenance risk is high (DMCA'd MPP repo, PhotonVision's hesitation).
   - *Bound:* `cv::imdecode` time for a 1600x1200 frame on an A76 vs `ffmpeg -hwaccel rkmpp -hwaccel_output_format drm_prime -f null`, then `vkGetPhysicalDeviceExternalBufferProperties(DMA_BUF, STORAGE)` on g24p0.
   - *Device:* Mali.
   - *Don't:*
     - export UVC vb2-vmalloc buffers into Vulkan. There is no per-frame cache maintenance, the GPU is non-coherent, and it's a silent stale-data hazard for 0.22 ms of gain.
     - use RGA for decimation. It box-averages and behaves differently per core, so it isn't bit-identical.
     - count on mainline V4L2. It has **no RK3588 JPEG decoder at all**; hantro there only encodes JPEG.
   - CSI cameras via rkisp (vb2-dma-sg/contig, NV12) are the cleanest zero-copy case if a deployment uses them.
2. **Driver hygiene.**
   - PanVK on Mesa 25.0 was about 13x slower (141 vs 11 ms at 720p).
   - Warn on `DRIVER_ID_MESA_PANVK`, and **re-measure on Mesa >= 25.2 / main**. Main now reports G610 as Vulkan 1.4 conformant with int64 atomics, 8-bit storage and conditional rendering. The 25.0 run probably fell back to the 4-byte/non-atomic64 paths, so check which caps were false.
   - A/B libmali g24p0 vs g29p1 with the same binary (`VK_DRIVER_FILES`, 10 min).
   - Try `CMAR_OPTIMIZE_FOR_LATENCY=1`, a config-key string found in libmali with undocumented semantics (5 min).
   - *Device:* Mali.

### B. Measure first: this decides everything in C

3. **malioc + hardware counters.**
   - PERFORMANCE.md s9's "no external profiler" is wrong for this GPU.
   - *malioc (Windows, about 1 h):* run `-c Mali-G610` over every shader with Mali's spec-constant values, and flag work registers > 32 (half occupancy, per Arm's Valhall guide) or any stack spilling. The llama.cpp Mali PR swung 17-24x on register-aware rewrites. It may also explain the two rejected vectorizations.
   - *On the Pi:* use Streamline via `gatord` for the CPU+GPU timeline (it shows scheduling bubbles directly), or libGPUCounters in the validator for per-span LS atomic issues, full/partial LS reads, L2/external bytes and all-register-warp %.
   - PanVK's `pipeline_executable_properties` gives register counts from the Mesa compiler today.
   - *Device:* Mali.

### C. GPU-side changes, all bit-identical by construction

4. **Drop the `shared wg_changed` + 2 `barrier()`s from `uf_merge`** and use `if (merged && changed_flag == 0u) atomicOr(changed_flag, 1u)`.
   - *Why:* the current code violates BP 3.4 s9.2/s9.3. The barrier prevents workgroup split/merge, and it is the "thread-0 setup / barrier / work / barrier / push" anti-pattern. The read-guard is essential, because merges are common in the first iteration and an unguarded global atomic would contend.
   - *Uplift:* estimated 2-10% of labelling, the largest span.
   - *Bound:* a one-line A/B.
   - *Device:* both.
5. **Per-shader-core privatization of extents via `gl_CoreIDARM`, plus 64-byte padding of `MinMaxExtentsGpu`.**
   - *Why:* today copy = `gl_WorkGroupID.x & 7` over a 32-byte struct, so all 4 cores hit every copy and two blobs share each line. BP s10.13 recommends per-core instances and 64-byte spacing, and the VK_ARM_shader_core_builtins spec names exactly this use.
   - *Watch out:* map core ids through `shaderCoreMask` rather than `& 7`, since ids can be sparse.
   - *Uplift:* 0.05-0.2 ms of the ~0.3 ms atomic overhead left in extents.
   - *Bound:* the padding alone is a one-constant change; per-core is about 20 lines.
   - *Device:* Mali (g24p0+/PanVK).
6. **Cross-frame GPU overlap on libmali's second queue** (one family, `queueCount = 2`; CSF).
   - *Idea:* frame N+1's front half runs on queue 1 while frame N's latency-bound tail runs on queue 0, filling the bubbles each of the ~31 barriers leaves.
   - *Uplift:* throughput only, not latency. Unknown size.
   - *Bound, no code:* run two `apriltag_vulkan_validate --loop` processes at once. Clearly more than 1.0x the single-process aggregate rate means the bubbles are real.
   - *Device:* Mali mainly.
7. **Barrier audit + command-buffer replay** (BP s3.9/s4.6; MNN's un-landed "reuse recorded commands"; the Arm sample shows pool reset is cheaper than per-buffer reset).
   - *Uplift:* barriers bounded at 0.1-0.5 ms; recording probably tens of us.
   - *Bound:* a deliberately wrong no-barrier build; the `cpu_record` span.
   - *Device:* both.
8. **Labelling working set vs the 1 MB L2** (RK3588 = 4x256 KB).
   - *Why:* at 1280x800 d2, `parent_buf_` alone is 1.0 MB (+256 KB thresholded), so `find()` chains miss L2 too. That fits "dependent-load bound, DMC-insensitive".
   - *Bound:* per-pixel labelling time at 1024x512 d2 (parent = 512 KB) vs 1280x800 d2, or the external-bytes counter.
   - *Fix if a step shows:* store parents per horizontal run. That is a large change and must keep root = min index.
   - *Device:* Mali (RDNA4 has 32 MB of Infinity Cache).
9. **Specialization constants for `width`/`height`/per-site flags** (BP s10.7).
   - *Uplift:* under 3%.
   - *Bound:* malioc instruction counts first.
   - *Device:* both.
10. **Invalidate only the bytes written on readback** (there is no coherent+cached memory type on RK3588).
    - *Uplift:* at most tens of us.
    - *Device:* Mali.

**Already compliant, so no action:** workgroup sizes for barrier-free shaders; one global COMPUTE->COMPUTE memory barrier; fences, not WaitIdle; robustBufferAccess off; pipeline cache; descriptors allocated once; push constants; no shared-memory tiling (ncnn and MNN reach the same conclusion); no fp16 (the pipeline is integer).

**Could not verify:**
- that libGPUCounters and gatord work on the RK3588 vendor CSF kbase;
- exact malioc flags and driver-revision selection (the docs page is JS-only);
- DMA_BUF import of a *storage buffer* on libmali (only OpenCL import is proven);
- whether kbase does its own cache maintenance for imported vmalloc dma-bufs;
- the RK3588 G610 `shaderCoreMask` value;
- `queueCount` on g24p0 (seen only on g6p0);
- the semantics of `CMAR_OPTIMIZE_FOR_LATENCY` and how it is read;
- PanVK performance on current Mesa;
- A76 software MJPEG decode time (OpenBenchmarking tjbench returned 403);
- whether later libmali versions add a coherent+cached memory type.

The RK3588 JPEG spec figures come from a vendor's copy of the Rockchip brief. The Rockchip PDF itself has only the block diagram, which confirms the 4x256 KB L2.

**Deliberately skipped:** ACL, VkFFT, Kompute, Geekbench. No technique is expected to transfer to this irregular integer pipeline, and the WebSearch budget ran out.
