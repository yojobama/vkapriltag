### Speeded Up Detection of Squared Fiducial Markers (ArUco3) — Romero-Ramirez, Munoz-Salinas, Medina-Carnicer (Univ. Cordoba), Image and Vision Computing, June 2018
- URL: https://doi.org/10.1016/j.imavis.2018.05.004 (cached: ccl/hash/aruco3.txt, fiducial/learned/aruco3.txt)
- Technique: Seven-step pipeline for *video*, every step exploiting a minimum-marker-size prior. (1) Resize input by factor c/tau_i, where c = 32 px canonical side and tau_i = c + max(W,H)*tau_i_norm is the minimum marker side the caller cares about (Eq. 1-2), so the smallest admissible marker becomes ~32 px on a side in the reduced image. (2) Replace ArUco's adaptive-mean threshold (a convolution) with a *global* threshold: if the previous frame found markers, Otsu on a histogram of the pixels of the detected markers picks the next frame's threshold; if not, up to 3 random thresholds in [10,240] are tried, running the whole pipeline each time. (3) Suzuki-Abe contours; reject perimeter < 4c; Douglas-Peucker; keep convex quads. (4) Build a 2x pyramid down to ~c x c. (5) Warp each candidate from the pyramid level whose contour perimeter is closest to 4c (Eq. 4) -> canonical 32x32 image in ~constant time regardless of marker size; Otsu + bit majority. (6) Corner upsampling: start at the pyramid level nearest the reduced image, upscale corners, cornerSubPix, repeat per level down to I0 (coarse-to-fine refine). (7) Next frame's tau_i = (1 - tau_s) * P(smallest detected marker)/4, tau_s ~ 0.1 accounts for motion ("markers 10% smaller than the smallest seen are still sought"); reset tau_i = 0 (full resolution) on any frame with no detections.
- Reported speed-up: 17x (4K, worst) to 40x (best) vs OpenCV ArUco, single thread, Intel i7-4700HQ. Mean per-frame time (Table 1): 0.903 ms 480p, 1.009 ms 600p, 1.133 ms 720p, 1.384 ms 1080p, 2.755 ms 4K -> ">360 fps at 4K, >1000 fps at 480p". Breakdown at 4K: resize 0.101, segmentation 0.351, contours 1.109, pyramid 0.476, code extraction 0.583 (~constant across resolutions — the pyramid warp is what makes it constant), corner upsampling 0.134 ms. Table 2: tau_i = 0.01/0.015/0.02/0.1/0.2 -> image-area reduction 0/31/48/82/90%; gains saturate beyond tau_i = 0.2. 1000 fps at 4K with tau_i = 0.1 (markers > 10% of image), 1000 fps at 1080p with tau_i = 0.05.
- Accuracy / determinism impact: TPR "behaves exactly like ArUco" above a minimum marker area; FPR = 0 in all tests (Fig. 7, 10,666 frames, 16-marker panel, 30 fps phone 4K video). Corner jitter (std dev of static corners, Table 3): ArUco 0.140 px, ArUco3 0.161 px, Chilitags 0.174, AprilTag (v1/v2-era impl) 0.225, ARToolKit+ 0.432 -> +0.02 px from working at reduced scale + pyramid refinement. Canonical size c < 32 hurts TPR; c > 32 gives nothing. Recall costs that are *not* measured in the paper: (a) any marker smaller than (1-tau_s) x the previously smallest is missed until a frame with zero detections resets tau_i to 0 — i.e. a new far tag entering while a near tag is tracked is never found (the paper explicitly lists "multiple markers with significantly different scales" as future work); (b) global threshold fails under strongly non-uniform lighting across the frame; (c) the random-threshold search on empty frames costs up to 3 full pipeline runs. Non-deterministic (random threshold search, frame-history-dependent).
- Applicability to vkapriltag: The *useful* transferable parts: (i) adaptive decimation from the previous frame's smallest tag (the AprilTag analogue is choosing quad_decimate per frame: decimate 2 -> 4 cuts GPU pixel work ~4x); (ii) coarse detect + full-res corner refine — AprilTag 3 already does exactly this with `refine_edges` on the full image after decimated detection, so the "pyramid corner upsampling" is already present in-tree in a different form; (iii) canonical-size decode independence — AprilTag decodes by sampling bit centers, already O(bits) not O(area), so no gain there. The global-threshold trick does not map (AprilTag's 4x4-tile min/max threshold is already cheap on GPU and is what gives lighting robustness). All of it breaks the bit-identical-to-libapriltag gate *per frame* unless exposed as an opt-in "tracking mode" whose output is bit-identical to libapriltag run at the chosen decimation. Mali and RDNA both benefit; bigger relative win on Mali where GPU time scales with pixel count (labelling 27%, preprocessing). Cheap bound: run the existing benchmark at decimation 2 vs 3 vs 4 at 1280x800 on the Orange Pi and record GPU ms + detection count on the PhotonVision test set.

### AprilTag 2: Efficient and robust fiducial detection — Wang & Olson (Univ. Michigan), IROS 2016
- URL: https://april.eecs.umich.edu/media/pdfs/wang2016iros.pdf (cached: fiducial/at2.txt, ccl/hash/apriltag2.txt)
- Technique: Replaces AprilTag 1's edge-first pipeline (gradient -> cluster edgels -> fit line segments -> search segment combinations for quads) with region-first: adaptive threshold (tile min/max) -> union-find CCL -> "continuous boundary segmentation" (cluster boundary pixels by the *pair* of black/white component IDs via a hash table) -> quad fit (sort boundary points by angle around centroid, cumulative moments give O(1) PCA line fit over any range, corners = peaks of line-fit MSE swept over a window, then try all 4-combinations of the candidate corner peaks and keep the min-MSE quad; prefilter by MSE, corner angle, >=4 corners) -> decode with a precomputed hash of all codewords within 2 bit errors (O(1) instead of O(n) family comparisons) -> optional edge refinement on the full-res image (sample gradient along each edge normal, gradient-weighted average, refit line, intersect). The paper explicitly trades away detection of partially occluded tags (a region-first detector needs the whole border) for speed.
- Reported speed-up: Single-thread Xeon E5-2640 2.5 GHz, LabelMe (421,049 natural images, no tags): 0.254 us/pixel new vs 0.374 us/pixel old (~78 vs 115 ms for 640x480) = 1.47x. With decimation 2: 0.072 us/pixel (~22 ms per 640x480) -> ~3.5x vs undecimated new, ~5.2x vs AprilTag 1.
- Accuracy / determinism impact: Candidate quads 51.1M (old) vs 13.6M (new); false positives 145 vs 6 on LabelMe with 36h11 and up to 2-bit correction (FPR 0.000284% vs 0.000044%, theoretical 0.000570%). Raytraced single-tag test: decimate-2 position/orientation error "not noticeably affected" vs full-res for the new detector, whereas the old detector degraded badly when decimated; new detector detects tags much farther (Fig. 7, 10 real Point Grey 1296x964, 0.167 m tags). Numbers for decimated accuracy are only given as plots, not tables. The paper says edge refinement "is not crucial if one is only interested in detecting tags" but improves pose accuracy.
- Applicability to vkapriltag: This *is* vkapriltag's pipeline (threshold + UF CCL + boundary hash grouping + moment-based quad fit). Key lesson for this category: the O(1)-range-moment trick is what makes corner search cheap; vkapriltag already computes the line-fit moments on GPU in `sort_points_local`. The decimate-then-refine trade (3.5x for negligible pose error) is the paper's own main speed lever and is where adaptive decimation (ArUco3-style) plugs in. The hash-table decode is already in upstream (`quick_decode`). Edge-based detection (AprilTag 1) is the slower, more occlusion-tolerant alternative — no speed reason to go back.

### Flexible Layouts for Fiducial Tags (AprilTag 3) — Krogius, Haggenmiller, Olson (Univ. Michigan), IROS 2019
- URL: https://april.eecs.umich.edu/papers/details.php?name=krogius2019iros (cached: fiducial/at3.txt, at3.pdf)
- Technique: Same high-level pipeline as AprilTag 2; speed-ups listed in Sect. III-C: (1) point-sampled decimation instead of box filter ("point sampling performs better for tag detection" — preserves edges); (2) union-find skips redundant unions when the neighbour pixel value equals the previous one (Fig. 5); (3) early rejection of connected components too small to produce a decodable tag; (4) atan2 sort key replaced by quadrant + slope key (Eq. 2, same order as the angle); (5) line-fit error = least eigenvalue of the 2x2 covariance (one sqrt instead of sin/cos); (6) homography via 8x8 Gaussian elimination with H33 = 1 instead of 9x9 SVD. Small-tag recall: bilinear sampling at cell centres + 3x3 Laplacian sharpening of the cell-value array (K = I + 0.25*Laplacian, Eq. 5) before decode.
- Reported speed-up: No per-step numbers. Fig. 7 speed-vs-recall sweep (Intel i7-7600U 2.8 GHz; 160+160 images 1296x964, 4 cm tags at 20-160 cm, face-on and 45 deg): AprilTag 3 decimation 1..24, AprilTag 2 decimation 1..17, ArUco3 (DM_FAST) minMarkerSize 0..0.11; AprilTag 3 curve dominates both (up to ~1000+ fps at high decimation with falling recall). Exact curve values are plot-only.
- Accuracy / determinism impact: The paper states decimation is *the* speed-recall knob, and that under high decimation 41h12 loses more recall than 36h11 (attributed to 36h11's effective white-border advantage on white backgrounds). Complexity metric (Ising energy) cuts LabelMe false positives. No pose-error numbers.
- Applicability to vkapriltag: All six listed speed-ups are already in upstream and hence in vkapriltag (point-sample decimate on GPU, min-size blob rejection in `select_blobs`, the slope sort key in `sort_points_local`, eigenvalue line-fit error, Gaussian-elim homography in the CPU decode). The Fig. 7 methodology — a *parameter sweep plotting fps vs recall on a set of tag sizes* — is the right way to evaluate any recall-risk speed-up here (tracking, adaptive decimation) before shipping. Tag-family choice: 41h12 (fewer border pixels, larger bits at same print size) is not a speed lever for FRC because the field uses 36h11.

### YoloTag: Vision-based Robust UAV Navigation with Fiducial Markers — Raxit, Singh, Newaz (Univ. New Orleans), arXiv 2409.02334, Oct 2024
- URL: https://arxiv.org/abs/2409.02334 (cached: fiducial/learned/2409.02334.txt); code github.com/RedwanNewaz/YoloTag
- Technique: YOLOv8 (lightweight variant, COCO-pretrained, 10 epochs) trained on 9,128/5,016/3,148 train/val/test frames of 8 fixed tag36h11 markers from a Bebop2 camera (856x480, 30 fps), auto-labelled with AprilTag then hand-fixed. Each marker ID is a detection class; the bounding box corners feed EPnP over all visible markers, then a 2nd-order Butterworth low-pass on the trajectory. No bit decoding at all.
- Reported speed-up: 55 fps YoloTag (Python, GPU, NVIDIA Quadro P2200) vs 24 fps AprilTag (C++, CPU, i7-10700) vs 3 fps DeepTag, all at 856x480. The AprilTag number is far below what libapriltag does single-threaded at 856x480 (tens of ms at decimation 1 per AprilTag 2's 0.254 us/px, i.e. ~100 ms single-thread at decimation 1 but ~10 ms at decimation 2 on a modern core), and the paper gives no decimation / thread settings — so the 2.3x ratio is not a fair detector comparison.
- Accuracy / determinism impact: Hausdorff distance to Vicon: YoloTag 0.2464 / 0.4404 m (spiral / rect trajectories), AprilTag 0.386 / 0.384, DeepTag 0.968 / 0.9177; Frechet 2.16/2.064 vs 2.18/2.10 vs 2.38/2.28. YoloTag's advantage is largely the Butterworth trajectory filter plus multi-marker EPnP, not corner precision (bbox corners are not tag corners under perspective). It can only recognise the 8 IDs it was trained on.
- Applicability to vkapriltag: Not applicable as a detector replacement: closed-set IDs, bbox (not corner) geometry, no bit-exactness, and the comparison baseline is weak. At most it supports "use an NPU detector as an ROI proposer" — see RKNN entry for feasibility. Already listed in-tree as "YoloTag: 55 vs 24 fps"; this entry records why that ratio should not be trusted.

### DeepArUco++: improved detection of square fiducial markers in challenging lighting conditions — Berral-Soler, Munoz-Salinas, Medina-Carnicer, Marin-Jimenez (Univ. Cordoba), arXiv 2411.05552, Nov 2024 (Image and Vision Computing 2025)
- URL: https://arxiv.org/abs/2411.05552 (cached: fiducial/learned/2411.05552.txt)
- Technique: Three CNN stages: YOLOv8n/s bounding-box detector -> 64x64 crop -> corner refinement (direct coordinate regressor, or heatmap regressor with f = 2..32 first-layer filters + blob-centroid extraction) -> rectify -> small CNN bit decoder, then Hamming match against the ArUco dictionary. Trained on synthetic "Flying-ArUco v2"; evaluated on a real "Shadow-ArUco" dataset with hard lighting.
- Reported speed-up: It is *slower* than the classical detector. Table 5, 800x600, ~10.9 markers/frame, i7-11700F + RTX 3090: yolov8n+direct 26.87 ms total (det 8.05, ref 3.41, dec 13.37) = 37.8 fps; yolov8s+heatmap 29.86 ms = 33.9 fps; classic ArUco 8.57 ms = 130.5 fps; DeepTag 142.76 ms = 28.7 fps (high variance). Corner refiners alone (Table 1): direct 3.29 ms, heatmap 6.2-6.9 ms per frame.
- Accuracy / determinism impact: Shadow-ArUco (Table 2): markers with 4 corners within 5 px and correct ID — yolov8s+heatmap 80.9%, yolov8n+direct 69.6%, classic ArUco 29.3%, DeepTag 43.6%; but mean corner error ArUco 0.72 +- 0.51 px vs 1.9-2.1 px for the learned pipelines (~3x worse). Decoder PR: Hamming threshold 3 gives recall 0.9476 at precision 1.0. Hallucinations in pitch-black scenes reported.
- Applicability to vkapriltag: Negative result for speed: on a 3090 the learned pipeline is 3x slower than CPU ArUco, and corners are ~3x less accurate — both disqualifying for FRC pose. The one transferable idea is a *learned detector used only for lighting-robust recall* with classical corner refinement, which does not make anything faster. Not bit-identical in any form.

### DeepTag: A General Framework for Fiducial Marker Design and Detection — Zhang, Zheng et al., IEEE TPAMI 2022 (arXiv 2105.13731)
- URL: https://arxiv.org/abs/2105.13731 (cached: fiducial/learned/2105.13731.txt)
- Technique: Two-stage CNN. Stage-1 on the full (resized 640x480) image predicts ROIs (bbox + 4 corners) and is decoder-agnostic; Stage-2 on each 256x256 rectified ROI predicts dense keypoints (corners, grid points) and per-keypoint bit symbols, iterated to refine the ROI; pose by PnP on many keypoints. Supports AprilTag/ArUco/ARToolKitPlus/TopoTag/RuneTag families. Paper also proposes a *tracking mode*: Stage-1 only (IDs known from earlier frames), or Stage-2 only with the ROI predicted from the previous frame's pose.
- Reported speed-up: Slower than classical. i7-11700K + GTX-class GPU (model name truncated in text), Python: full pipeline ~23 fps for one marker at 640x480; Stage-1 CNN 0.013 s GPU (0.297 s CPU); Stage-2 per ROI count 1/2/4/8 = 0.019/0.031/0.057/0.108 s total with GPU (CNN part ~0.007-0.011 s; post-processing is serial CPU and dominates). Tracking with Stage-1 alone: 40 fps at 640x480; Stage-2 alone with pose-predicted ROI: 53 fps for one marker. Table 4 (1280x960, single marker, noise-free): AprilTag ~0.011 s (C++ CPU) vs DeepTag ~0.065 s; classical methods slow down with noise (AprilTag ~0.018 s at noise STD 300), DeepTag is flat.
- Accuracy / determinism impact: Yu's (TopoTag) dataset, AprilTag 36h11: original detector ~3.2 mm position error and ~76% recall vs DeepTag ~1 mm and ~99% recall (values read from a pdftotext-garbled Table 1 — column alignment approximate). Big recall gains under blur/noise/large view angle; DeepTag keypoint-rich custom markers (AprilTag-XO/XA) improve pose further.
- Applicability to vkapriltag: No speed transfer (6x slower than CPU AprilTag at 1280x960). Two ideas worth recording: (1) the tracking decomposition — once IDs are known, a cheap per-ROI refinement stage with ROI predicted from the previous pose; the classical analogue is running vkapriltag's CPU quad-fit + decode only on predicted ROIs; (2) the dense-keypoint pose (more points than 4 corners) improves accuracy but needs a custom marker, irrelevant for FRC's fixed 36h11.

### TopoTag: A Robust and Scalable Topological Fiducial Marker System — Yu, Hu, Dai, IEEE TVCG 2020 (arXiv 1908.01450)
- URL: https://arxiv.org/abs/1908.01450 (cached: fiducial/learned/1908.01450.txt)
- Technique: Marker identified purely by region-adjacency topology (black border -> white regions -> black child dots; baseline node fixes rotation, so no 4-rotation decode). Detection: threshold map computed on a downsampled image (scale s1, then further s2), bilinearly upsampled; binarize; build the region adjacency tree and filter topologically; all dot centroids (not just 4 corners) feed PnP + Levenberg-Marquardt.
- Reported speed-up: Table 2 (1280x960 global-shutter, 38.8 fps capture, 10 ms exposure, robot-arm trajectories; per-frame run time): ARToolKit 5.9 ms, ARToolKitPlus 9.3 ms, ArUco ~54-56 ms, RuneTag 455.8 ms, ChromaTag 9.1 ms, TopoTag 33.6 ms; AprilTag reported as "AprilTag-1 / AprilTag-2" pairs: 16h5 246.8 / 15.1 ms, 25h9 244.4 / —, 36h11 251.3 / 13.6 ms, 36h9 241.3 / 13.4 ms (pairing read from garbled extraction — the ~240-250 ms values are AprilTag-1, the ~13-15 ms values AprilTag-2). => the edge/gradient-based AprilTag-1 is ~18x slower than the threshold+CCL AprilTag-2 on the same images, single CPU.
- Accuracy / determinism impact: Recall/precision (Table 2): AprilTag 36h11 100/99.99%, 16h5 77.3/99.88%, 25h9 80.4/100%, TopoTag 100/100%, ChromaTag 9.1/9.2% (fails on this grayscale-ish set), RuneTag 0.28%. TopoTag reports lower pose error than square markers thanks to many more correspondences (tables not re-read here). Paper notes AprilTag-2 has better min-range but worse max-range than AprilTag-1 and attributes it to the switch from gradient-based to adaptive-threshold segmentation *for speed* — i.e. the region-based pipeline costs some far-tag recall.
- Applicability to vkapriltag: (1) Confirms the region-first pipeline vkapriltag already uses is an order of magnitude faster than edge-first (AprilTag-1), so edge-based quad detection is not a speed direction. (2) Threshold-map-on-downsampled-image is what AprilTag's 4x4-tile min/max already is. (3) Topological IDs avoid the 4-rotation decode, but FRC uses 36h11. No new lever.

### ChromaTag: A Colored Marker and Fast Detection Algorithm — DeGol, Bretl, Hoiem (UIUC), ICCV 2017 (arXiv 1708.02982)
- URL: https://arxiv.org/abs/1708.02982 (cached: fiducial/learned/1708.02982.txt)
- Technique: Colour tag (red inner square / green ring, two shades each, 16h5 code) + a *sparse, seed-driven* detector: sample only every N-th row and column (FindADiff, LAB 'A'-channel jump > 25 vs previous grid sample; cells assumed >= N/2 px), skip grid points inside already-detected tags; from a hit, ray-scan up/down/left/right to find the red-green border and re-centre; greedily grow a convex polygon by scanning in the direction of max potential added area until area ratio > 0.98; K-means (K=4) on edge angles -> quad; GoodFeaturesToTrack-style corner refinement; homography, sample, hash-table decode. Most false candidates are rejected by the colour-difference test before any geometry work.
- Reported speed-up: 752x480, i7 Ivy Bridge 3.5 GHz, one thread (Table 1): ChromaTag average 926.4 fps vs AprilTag (2, 16h5) 56.1, CCTag 10.0, RuneTag 41.9 fps => 16x / 92x / 22x. True-positive frames 709.2 vs 56.3 fps (12x); frames with no detection 2616.1 fps. Per-step (Table 2, detection frames): FindADiff 0.52 ms, InitialScan 0.03, BuildPolygon 0.08, PolyToQuad 0.74, Decode 0.04 ms.
- Accuracy / determinism impact: Recall is much lower than AprilTag: ChromaTag 64.0/67.9% (WB/NWB) vs AprilTag 96.4/98.2% on the same sequences (Table 3); recall matches AprilTag only for tags > ~70 px (sqrt area) at 752x480. Precision: ChromaTag ~96-97% vs AprilTag 16h5 ~43-46% (16h5 false positives). Corners: 94.4% of ChromaTag corners within 3 px of hand-labelled vs 89.1% for AprilTag (94.2% within 4 px).
- Applicability to vkapriltag: Colour tags are out (FRC field). The transferable idea is *sparse seeding*: only analyse regions touched by a coarse grid of "edge-present" samples. vkapriltag's GPU already processes every decimated pixel at ~3.3 us per 1k source pixels on Mali, so a grid-seeded mask could skip CCL work in flat tiles — but AprilTag's tile threshold already marks low-contrast tiles as 127 (ambiguous) and `uf_init.comp` already never joins 127 pixels, so flat regions are already cheap; the residual gain would be launching labelling/`blob_diff` threads only over non-flat 4x4 tiles (indirect dispatch over a tile list) — exact, but saves only the per-pixel read + trivial work, probably a few % on Mali (unmeasured). Recall risk only if the grid is coarser than the smallest tag; the 16x is bought with a 30-point recall loss on small tags.

### Determining and Improving the Localization Accuracy of AprilTag Detection — Kallwies, Forkel, Wuensche (UniBw Munich), ICRA 2020
- URL: https://doi.org/10.1109/ICRA40945.2020.9197427 ; project page https://www.mucar3.de/icra2020-apriltags/ ; code https://github.com/UniBwTAS/apriltags_tas (cloned: fiducial/algo/apriltags_tas)
- Technique: Benchmarks corner localisation of AprilTag 3, AprilTags C++ (Kaess, the AprilTag-1 port), ArUco and OpenCV-ArUco on a dataset with sub-pixel ground truth; also covers processing time (numbers not accessible, see below). Proposes (a) a "cross-corner" filter: adaptive-threshold + morphology, then sample a radius-5 circle around each corner at 10-degree steps and count black/white sections, dropping detections whose corner neighbourhood is not a clean 2-section corner (catches partial-border occlusion); (b) "direct edge optimisation": for each edge, mask a 5-px-thick band along the detected edge (excluding 10x10 around corners) and fit the line (normal, offset) with Ceres (numeric central differences, DENSE_QR, up to 100 iterations) so that a bilinear 0->255 step template, positioned by signed distance to the line, matches raw pixel values; corners = intersections of the refined lines. Code: `apriltags_tas/src/apriltag_detector.cpp` lines 132-262.
- Reported speed-up: None — this is an accuracy method. The per-tag cost is a nonlinear least-squares with ~(4 x 5 x edge_length) residuals and numeric differentiation, i.e. orders of magnitude more CPU than AprilTag 3's `refine_edges` (which samples a handful of points per edge). Paper's own timing table not accessible.
- Accuracy / determinism impact: Abstract: median corner error 0.017 px with the new edge refinement vs 0.17 px for standard OpenCV corner refinement (cornerSubPix) — 10x. Project page: all detectors localise fronto-parallel tags better; AprilTag 3 and AprilTags C++ show "significantly higher error" for axis-aligned ("straight") tags; ArUco unstable with small (4 deg) rotations. AprilTag 3 reportedly best overall indoors.
- Applicability to vkapriltag: Defines the accuracy ceiling: AprilTag 3's corners are not sub-0.1 px, so shortcuts that move corners by < ~0.05 px are below the detector's own error — but the bit-identity gate makes that argument moot for the default path. The straight-tag error finding is relevant to FRC (tags are mounted upright, cameras often near-level): a cheaper version of edge-model fitting (Gauss-Newton on a step-edge model with analytic Jacobian, run only on the few accepted tags, possibly on GPU) could be an *optional* accuracy upgrade replacing `refine_edges`, not a speed-up. Cost of the Ceres version per tag unknown; bound it by timing apriltags_tas on a 1280x800 frame with ~4 tags.

### Analysis and Improvements in AprilTag Based State Estimation — Abbas, Aslam, Berns, Muhammad, Sensors 19(24), Dec 2019
- URL: https://pmc.ncbi.nlm.nih.gov/articles/PMC6960891/
- Technique: Characterises AprilTag (2) pose error on a mobile robot vs distance and camera yaw relative to the tag; proposes Soft Yaw Axis Correction (trigonometric correction toward the tag centre), an active yaw gimbal (PID at 10 Hz) keeping the tag centred, and a Gaussian-process sensor model for particle filters.
- Reported speed-up: None (slow-down): raw AprilTag 90 ms/frame, +SYAC 130 ms, +gimbal 125 ms, combined 255 ms (~4 Hz) on their platform.
- Accuracy / determinism impact: Off-axis yaw is the dominant pose-error source: at 70 cm, yaw 110 deg gives ~16 cm x-error vs ~2 cm aligned; at 30 cm ~1.0 cm (x) / 0.4 cm (y) mean error. Combined corrections: 4.4 -> 0.8 cm (x), 2.56 -> 0.54 cm (y) at 70 cm.
- Applicability to vkapriltag: Only as accuracy context: pose error from geometry (view angle, distance) is in the centimetre range, far larger than anything a sub-0.1 px corner change causes — relevant when arguing that a recall-neutral shortcut (e.g. decimation 2 -> 3 with refine_edges) is accuracy-acceptable. No speed technique.

### STag: A Stable Fiducial Marker System — Benligiray, Topal, Akinlar, Image and Vision Computing 2019 (arXiv 1707.06292)
- URL: https://arxiv.org/abs/1707.06292 (cached: fiducial/learned/1707.06292.txt)
- Technique: Edge-based (not threshold+CCL) pipeline: EDPF (parameter-free Edge Drawing) edge segments -> EDLines line segments -> quad candidates from line-segment corners -> perspective validation -> decode (48-bit codes) -> localise the inner circular border as an ellipse from edge-segment loops and use the circle-ellipse (conic) correspondence to refine the homography — ellipses fitted to all border samples localise better than quads from 4 lines (Fig. 3-4 simulation, 10,000 trials).
- Reported speed-up: Per-step on 1280x720 cluttered scene, one marker (Table 2): EDPF 22.6 ms, EDLines 1.0, candidate detection 0.7, validation 0.6, ellipse localisation 1.1, homography refinement 0.8, total 26.8 ms — edge detection is >80% of the time and "partly sequential"; authors cite a CUDA Edge Drawing with up to 12x (-> ~4.4x for STag overall). Table 7 (Xeon, 1280x720, one marker): ARToolKit+ 2.6 ms, ArUco 10.0 ms, RUNE-Tag 579.9 ms, STag 18.1 ms.
- Accuracy / determinism impact: STag is detected at larger view angles than ARToolKit+/RUNE-Tag and has lower pose jitter than ArUco; more prone to pose ambiguity than ARToolKit+ at distance. RUNE-Tag fails at distance/angle.
- Applicability to vkapriltag: Evidence *against* an edge/line-segment-detector front end for speed: even with EDLines (one of the fastest LSDs) the edge extraction dominates and is sequential; the threshold+CCL front end is ~2x cheaper per pixel on CPU (ArUco 10 ms vs STag 18 ms here) and is already GPU-parallel in vkapriltag. The conic-refinement accuracy trick needs circular features — not in 36h11.

### E2ETag: An End-to-End Trainable Method for Generating and Detecting Fiducial Markers — Peace, Psota, Liu, Perez (Univ. Nebraska-Lincoln), BMVC 2020 (arXiv 2105.14184)
- URL: https://arxiv.org/abs/2105.14184 (cached: fiducial/learned/2105.14184.txt)
- Technique: Jointly trains 30 marker patterns (via transposed conv) and a fully convolutional ResNet18-based detector/classifier/corner regressor under heavy synthetic augmentation.
- Reported speed-up: 10 fps on 640x640 (MATLAB, i9-9900K + RTX 2080 Ti) vs ChromaTag ~900 fps and AprilTag ~50 fps quoted by the authors — 5x slower than AprilTag.
- Accuracy / determinism impact: Higher precision than AprilTag/ChromaTag under all conditions, better recall at steep angles, very small tags, noise and low contrast; AprilTag has higher recall on mid-size tags. Closed set of 30 classes; 26.8-40.7% classification accuracy on tiny (<= 32 px) markers in the confusion test.
- Applicability to vkapriltag: None for speed. Confirms the pattern across all learned detectors in this file (DeepTag, E2ETag, DeepArUco++, YoloTag): on desktop GPUs they are slower than CPU AprilTag, and their wins are recall under blur/noise/lighting, not throughput.

### LFTag: A Scalable Visual Fiducial System with Low Spatial Frequency — Ben Wang (UPenn), arXiv 2006.00842, Jun 2020
- URL: https://arxiv.org/abs/2006.00842 (cached: fiducial/learned/2006.00842.txt)
- Technique: Topological marker (TopoTag-like) with relative-position encoding; a staged rejection cascade (topological filter -> area -> geometry -> angle -> collinearity -> residual error). Also measures AprilTag 3 false positives on LabelMe at decimation 2 for each family and hamming setting.
- Reported speed-up: No timing tables of interest.
- Accuracy / determinism impact: Table I (LabelMe, 266,995 tag-free images, AprilTag 3, decimation 2) false-positive detections for max-hamming 0 / 1 / 2: 16h5 (30 codes) 2,262 / 44,577 / 412,243; 25h9 3 / 119 / 1,430; 36h11 (587 codes) 0 / 2 / 7; 41h12 0 / 0 / 3. Table II shows how a rejection cascade cuts 1.19M topological candidates to 1 false positive, with each cheap geometric stage removing ~40-60%.
- Applicability to vkapriltag: (1) Family choice: 36h11 at max-hamming 2 is essentially false-positive-free, so FRC can keep full correction; 16h5 needs hamming 0. (2) Decode-cost angle: the number of candidate quads that reach `quad_decode` is what the CPU tail pays for, and LFTag's Table II is a template for measuring per-stage rejection rates of cheap pre-decode tests on vkapriltag's own candidates (in-tree idea C4). (3) Current upstream `quick_decode` (cached fiducial/apriltag/apriltag.c lines 209-338) is no longer the AprilTag-2 "all codes within 2 bits" hash: it is a pigeonhole chunk index (code split into NUM_CHUNKS chunks; a codeword within maxhamming <= 3 errors must match at least one chunk exactly), scanned for each of 4 rotations with a popcount per bucket entry. So the codeword lookup is already cheap and nearly independent of maxhamming; per-candidate decode cost is dominated by the homography, bit sampling (bilinear + sharpening) and — when enabled — `refine_edges`, not by the Hamming search.

### FMAC: a Fair Fiducial Marker Accuracy Comparison Software — Laurent & Sandoz (Univ. Marie et Louis Pasteur / FEMTO-ST), arXiv 2601.07723, Jan 2026
- URL: https://arxiv.org/abs/2601.07723 (cached: fiducial/learned/2601.07723.txt); code https://github.com/vernierlib/fmac

### WhyCon: A Practical Multirobot Localization System — Krajnik, Nitsche, Faigl et al., J. Intelligent & Robotic Systems 76(3-4):539-562, 2014
- URL: https://link.springer.com/article/10.1007/s10846-014-0041-x ; code https://github.com/gestom/whycon-orig (cloned: fiducial/algo/whycon-orig)
- Technique: Circular black ring / white centre marker. The detector is a flood-fill segmenter that *starts scanning at the pixel where the marker was in the previous frame* (`CCircleDetect::findSegment`, `init.valid && track` -> `ii = init.y*width + init.x`), flood-fills the dark segment, tests area ratio / circularity / concentricity / B-W contrast, and on success stops immediately — so a tracked frame touches only ~the marker's pixels. On failure it continues the linear scan from there and wraps around the whole image (full search), so recall is preserved at the cost of that frame's time. The processing buffer is cleaned only inside the previous bounding box (+2 px) when tracking succeeded (`bufferCleanup`). The binarisation threshold for the next frame is set to the mean of the inner and outer segment intensities (same idea as ArUco3's Otsu-on-markers).
- Reported speed-up: Abstract (Semantic Scholar / search summary): "process hundreds of images per second while tracking hundreds of objects with millimeter precision"; README: 80-100 Hz update rate. Per-configuration tracked-vs-untracked timings are in the paper body, which I could not open (Springer login; repository PDFs not reachable).
- Accuracy / determinism impact: Tracking does not change the detection result when the marker is found at its previous position (same segment is found either way); a missed track costs a full-frame scan in the same frame, so no recall loss — only variable latency. Threshold adaptation makes output history-dependent.
- Applicability to vkapriltag: The key design lesson is **"ROI first, full-frame fallback in the same frame"**, which removes the recall risk of pure ROI tracking at the cost of worst-case latency (ROI pass + full pass when a tag is lost). For vkapriltag: run the GPU pipeline on the union of predicted ROIs; if any tracked ID is missing or on every Nth frame, run the full frame. New tags entering are still found only on full-frame frames — that residual recall risk remains. The flood-fill-from-seed itself does not map to a GPU CCL.

### ArUco Nano: a simpler, faster, and more reliable fiducial marker detector — Munoz-Salinas, Romero-Ramirez, Garrido-Jurado, SoftwareX 2026
- URL: https://www.sciencedirect.com/science/article/pii/S2352711026001822 ; code https://github.com/rmsalinas/aruco_nano (cloned: fiducial/algo/aruco_nano)
- Technique: 700-line header. (1) Threshold = box filter (15x15) minus image, fixed offset (replaces cv::adaptiveThreshold, "~1.5x speed up" per code comment). (2) "Visited-aware tracing" replaces cv::findContours: single scan with SIMD skip-to-next-foreground / skip-to-end-of-run, 8-connected Moore tracing that marks pixels VISITED and counts revisits; contours with revisits > 5% of their length (thin, self-touching noise) or shorter than 4*minSize are dropped during tracing. (3) approxPolyDP + min side length. (4) Decode by *direct bilinear sampling of the cell centres through the homography* (no canonical-image warp), then a cascade: plain threshold -> local adaptive threshold on the bit array -> Otsu, trying the next only if the previous fails to decode. (5) cornerSubPix only on accepted markers.
- Reported speed-up: README (i7-13700H, single thread vs OpenCV ArUco): 1 MP 6.68 vs 43.46 ms (6.5x), 4 MP 22.93 vs 125.00 ms (5.4x), 16 MP 101.67 vs 504.27 ms (4.9x); "2x faster than the multi-threaded implementation". Paper abstract also claims higher F1 than OpenCV on up to 16 MP images.
- Accuracy / determinism impact: Deterministic; claimed higher F1 than OpenCV. Corner accuracy governed by cornerSubPix as in OpenCV.
- Applicability to vkapriltag: The speed tricks here are what AprilTag 3 already does in its own way (cheap tile threshold instead of convolution; boundary extraction without a general contour tracer; decode by sampling cell centres, not by warping). Two ideas map to the CPU tail: (a) *revisit-ratio rejection* is a cheap proxy for "this boundary is noise" — AprilTag's analogue is rejecting blobs whose boundary-point count is large relative to their bbox perimeter before `fit_quad`; (b) *cascaded decode* — try the cheap path first, fall back only on failure — matches the in-tree observation that the CPU `quad_decode` fallback rate (2.94% at decimation 2) is what drives the tail. Neither is bit-identical unless the rejection is provably a subset of what upstream rejects.

### ROI cropping in practice + exactness analysis against upstream code — OpenMV forum (2020), AprilRobotics/apriltag #105, upstream `apriltag_quad_thresh.c` / `apriltag.c`
- URL: https://forums.openmv.io/t/apriltag-speed-up-with-dynamic-roi/2054 ; https://github.com/AprilRobotics/apriltag/issues/105 ; code cached at fiducial/apriltag/
- Technique: OpenMV "dynamic ROI": after a detection, the next frame is searched only in the previous tag rect grown by 0.33 x width/height on each side; if nothing is found in the ROI, the *next* frame is searched in full (one-frame recovery delay). Upstream #105 (closed): maintainer mkrogius — "crop the image yourself and then transform the corner location back ... before doing pose estimation"; no ROI API upstream. Code analysis of what a crop preserves: (1) `threshold()` uses 4x4 tiles anchored at the image origin with a 3x3-tile min/max dilation, and partial last tiles reuse the last full tile, so a crop whose origin is a multiple of 4 decimated px (4*d source px) and that keeps >= 1 full tile of margin around the tag reproduces the thresholded values of the interior exactly; (2) `image_u8_decimate` point-samples from the origin, so the crop origin must also be a multiple of d; (3) corners are scaled by `*= quad_decimate` after `fit_quad`, and `refine_edges` / decode sample the *full-resolution* original, so they need the full image or a larger margin; (4) `detection_compare_function` sorts the final detections, and the overlap dedup (`g2d_polygon_overlaps_polygon`) runs after decode, so detection order does not depend on label ids; (5) `nclustermap = 0.2*w*h` sizes only the hash table, not the result.
- Reported speed-up: OpenMV H7 Plus 22 fps at VGA with dynamic ROI (no no-ROI baseline stated in the post). In-tree cost model (PERFORMANCE.md s.3): Mali GPU ~= 560 us + 3.3 us per 1k source px, so a 25% ROI takes 1280x800 from ~3.9 to ~1.4 ms.
- Accuracy / determinism impact: Two non-exactness sources remain even with an aligned crop: (a) **floating-point origin** — moments/line fits computed in crop-local coordinates round differently from full-frame ones, so adding the offset after the fit is exact only to ~1e-6 px, not bit-exact; (b) **connectivity** — a white (or black) component that is connected only through pixels outside the crop is split into two labels, which splits a (black, white) boundary cluster and can lose the tag or change its point set. (a) is removable by emitting boundary points in full-frame integer coordinates on the GPU (push-constant origin added before `PackXY`), after which the moments are the same sums as the full-frame run. (b) is inherent but only bites when the tag's own white quiet zone is interrupted inside the margin. Duplicate removal is safe across overlapping ROIs: upstream's overlap dedup prefers lower hamming, then larger decision margin, then compares corner coordinates, so its outcome is order-independent (tie-broken by geometry, not by label ids or list order).
- Applicability to vkapriltag: Makes in-tree idea C1 (temporal ROI) **bit-identical per found tag** in the common case, provided: crop origin aligned to lcm(4*d, d) = 4*d source px; margin >= 1 tile + motion allowance; boundary points emitted in full-frame coordinates; `refine_edges`/decode given the full frame (already the case — the CPU tail samples the full image). The remaining risk is recall only (tags outside the ROI, split components). Both devices; the win is on Mali (pixel-proportional 86%), RDNA's 0.66 ms has a larger fixed share. Cheap bound: run upstream libapriltag on aligned crops of the PGM corpus around each ground-truth tag and diff the detections against the full-frame run — no GPU work needed to prove the exactness claim.
- Verification: code analysis [verified from primary source: upstream C in cache]; OpenMV numbers [verified from primary source: forum post via fetch summariser]; #105 [verified from primary source: GitHub API]

### EagleEye "temporal acceleration" (field-map pose-projected ROIs) — Scythe Engineering (FRC), Chief Delphi thread + repo, 2025-Sep 2026
- URL: https://www.chiefdelphi.com/t/eagleeye-photonvision-alternative-with-120-apriltag-fps-on-raspi-5/523976 ; https://github.com/Scythe-Engineering/EagleEye-Vision-System (cloned: fiducial/algo/eagleeye) ; results file from PR #174 head: `benchmarks/temporal-performance-results.md` (cached: fiducial/algo/eagleeye_temporal_results.md)
- Technique: FRC-specific ROI tracking that removes most of the "new tag entering" recall hole. The Rust `TemporalAcceleration` takes the *field layout* (all 32 tag corners in world coordinates) and last frame's PnP camera pose, keeps tags that face the camera, lie in the padded frustum and (optionally) within `max_detection_distance_m`, projects them, pads by `padding_factor` (0.35 default) and returns up to `max_regions` (20) crops of >= `min_region_size_px` (16). So a tag that was *not* seen last frame but is geometrically visible from the last pose is still searched. Crops are **perspective-rectified quads** (3x3 mapping) by default, detected with libapriltag (1 thread per crop; a separate 2-thread detector for full-frame searches), `quad_decimate` 2 normally and 3 for ROIs >= 96 px, `refine_edges` on; corners are mapped back through the 3x3. Fallback (`AprilTagDetector.detect`): if *all* crops yield zero detections, the full frame is searched in the same frame; if no pose can be projected, a single full-frame region is returned.
- Reported speed-up: Forum: 120 fps at native 1280x800 on a Raspberry Pi 5, 60 fps per camera with three cameras, "~3x faster" than PhotonVision at decimation 2 (forum claims, not in the results file). Results file (Pi 5, 1280x800, 22,080 frames of 7 synthetic 120 Hz match clips, pipeline time excluding video decode): production mean 10.6 ms / p95 27.3 ms over all frames; frames with tags 9.8 ms; frames without tags 20.6 ms (the full-frame fallback path); ROI-only frames (905 frames, no full-frame call) **3.48 ms mean, detector stage 0.89 ms**. So ROI-only frames are ~6x cheaper than tag-free (full-frame) frames on the same CPU. The authors state the 10.6 ms mean does *not* sustain 120 Hz.
- Accuracy / determinism impact: Full-frame vs cropped detections on 25 real images: **max corner difference 0.334 px**; position std [2.1, 4.9, 3.5] cm full-frame vs [2.5, 5.8, 4.0] cm cropped (cropped is ~20% noisier — rectifying warp resamples the image). Recall of temporal vs full-frame was **not measured** ("official eligible recall remains null"; provisional matching only). Rejected in their screens: padding 0.25 instead of 0.35 and *axis-aligned* crops both lost matches and poses; larger ROI decimation gave no convincing gain. Forum: adaptive decimation "didn't get much change ... vs static"; decimation mattered mostly when a tag fills most of the frame.
- Applicability to vkapriltag: The most directly relevant prior art for in-tree C1. Three transferable points: (1) **predict ROIs from the field map + last pose, not only from last frame's detections** — this is what makes ROI tracking safe for FRC, because a tag entering view is predicted from geometry; it needs the camera pose and field layout that PhotonVision already has. (2) Use **axis-aligned, tile-aligned crops, not rectifying warps**, to keep bit-exactness (see the ROI-exactness entry above) — EagleEye's 0.334 px / +20% pose noise is the cost of the warp, not of cropping; their finding that axis-aligned crops lost matches is probably a padding/shape issue (a rectified crop wastes fewer pixels for a skewed tag), so axis-aligned crops will need somewhat more padding. (3) Same-frame full-frame fallback only when *all* ROIs are empty bounds worst-case latency at ~ROI + full frame. On Mali the GPU cost model (560 us + 3.3 us/kpx) gives ~1.2-1.6 ms for two 400x400 ROIs vs 3.76 ms full frame — but vkapriltag would need multiple ROI dispatches per frame (per-ROI detector instance or a batched multi-ROI dispatch), and the 560 us fixed cost is per GPU submission chain, so batch all ROIs in one chain. RDNA gain small (fixed costs dominate at 0.66 ms). Cheap bound: EagleEye's own synthetic 7-clip dataset + replay harness is public; replaying its ROI decisions through vkapriltag's existing benchmark (crop -> detect) gives both ROI area fraction and fallback rate without writing GPU code.

### Detection and Accurate Localization of Circular Fiducials under Highly Challenging Conditions (CCTag) — Calvet, Gurdjos, Griwodz, Gasparini, CVPR 2016
- URL: https://openaccess.thecvf.com/content_cvpr_2016/papers/Calvet_Detection_and_Accurate_CVPR_2016_paper.pdf (cached: fiducial/algo/cctag.txt) ; code https://github.com/alicevision/CCTag (CPU + CUDA)
- Technique: Concentric black rings on white; detection by gradient-field voting for ellipse centres (edge points vote along the gradient direction), then a cascade that recovers ring arcs, fits the inner ellipse, and identifies by a 1-D radial cut profile through the imaged centre (projective-invariant ring ratios). - Applicability to vkapriltag: None for speed — a GPU port of a vote-based circular detector runs ~25x slower than vkapriltag's Mali phase on a desktop GPU. Also incompatible with FRC's 36h11 field. Confirms (with STag, TopoTag, AprilTag 1) that robustness-oriented, gradient/edge-voting front ends are an order of magnitude more expensive than the threshold+CCL front end, including on GPU.

### Chilitags tracking modes (KLT between detections) — Bonnard, Lemaignan, Zufferey, Mazzei, Cuendet, Li, Ozgur, Dillenbourg (CHILI lab, EPFL), library 2013-2014
- URL: https://github.com/chili-epfl/chilitags (cloned: fiducial/algo/chilitags; `include/chilitags.hpp`, `src/Track.cpp`)
- Technique: Square-marker detector with a separate *tracker*: for each tag known from a previous call, grow an ROI 2x around its corners, run pyramidal Lucas-Kanade (`calcOpticalFlowPyrLK`, 21x21 window, 3 levels, 30 iterations / eps 0.01) on the 4 corners from the previous frame to the current one, refine corners, keep only if all 4 corners tracked and the quad is convex. Modes: `DETECT_ONLY`, `TRACK_ONLY` (cannot find new tags, can lose some), `TRACK_AND_DETECT` (default — track, then full detection overrides; improves motion-blur robustness), `DETECT_PERIODICALLY` (full detection 1 in 15 frames by default, KLT otherwise), and `ASYNC_DETECT_PERIODICALLY/ALWAYS` (full detection in a background thread, only tracking in the caller's frame loop). Also: disabling corner refinement "reduces processing time by ~33%"; `setMaxInputWidth` downscales input (tags < 20 px then lost).
- Reported speed-up: Only qualitative in the code docs: "Tracking is drastically faster than full detection"; no numbers published in the repo.
- Accuracy / determinism impact: KLT-tracked corners are not detector corners — they drift and have no ID check; the library warns tracking "can at best return tags previously found; it won't find new ones, but can lose some", and that tracking over unrelated images "most likely generates false positives".
- Applicability to vkapriltag: Rejected as a speed path for the default output: KLT-tracked corners are neither bit-identical nor ID-verified, so they would inject unverified poses into PhotonVision's estimator. The *ASYNC* mode is the one interesting structural idea — decouple a slow full-frame detection (background) from a fast per-frame ROI path — which for vkapriltag is the same as idea 1's "full frame every N frames", except that the full-frame pass could run on a separate queue/frame without blocking the ROI frames (vkapriltag's FramePipeline already overlaps GPU and CPU; an async full-frame pass on Mali would compete for the same GPU, so only a *scheduled* every-Nth-frame full pass makes sense there). Both devices.
- Verification: [verified from primary source: code + header docs]

### TartanCalib: Iterative Wide-Angle Lens Calibration using Adaptive SubPixel Refinement of AprilTags — Duisterhof, Hu, Teng, Kaess, Scherer (CMU AirLab), arXiv 2210.02511, Oct 2022
- URL: https://arxiv.org/abs/2210.02511 (cached: fiducial/algo/tartan.txt)
- Technique: Calibration pipeline on AprilGrid targets for wide-angle lenses. Uses an intermediate camera model to (1) undistort into virtual pinhole views for detection, (2) *reproject the known target into the image* to predict features the detector missed, and (3) adaptive sub-pixel refinement: `cornerSubPix` with a per-feature search window scaled to the distance to the nearest reprojected neighbour (Eq. 3), or a symmetry-based refinement (Schops et al.) for high distortion.
- Reported speed-up: None (calibration, offline). The iterative pipeline "typically only takes 2-3 times longer to run compared to the non-iterative baseline".
- Accuracy / determinism impact: Abstract: reprojection error improved by up to 26.59%, up to 42.01% more features detected, on wide-angle lenses.
- Applicability to vkapriltag: Two indirect lessons. (1) "Reproject the known target, then look there" is the calibration-world version of EagleEye's field-map ROI prediction, and TartanCalib shows it *increases* recall (42% more features) rather than costing it, when the geometry model is good — supporting idea 1. (2) Fixed-window corner refinement is scale-fragile: AprilTag's `refine_edges` has the same issue in spirit (fixed sampling range along the edge normal, scaled with decimation). Relevant to wide-FOV FRC cameras (PhotonVision recommends ~100 deg diagonal), where the detector operates on the distorted image. Not a speed lever; no change to the bit-exact path.
- Verification: [verified from primary source]

### Three more learned-marker papers from the cache: Deep ChArUco (Magic Leap, arXiv 1812.03247, 2019), Ghost-DeblurGAN for fiducials (Liu et al., York Univ., arXiv 2109.03379, 2022), DeepFormableTag (Yaldiz et al., KAIST, arXiv 2206.08026, SIGGRAPH 2021)
- URL: https://arxiv.org/abs/1812.03247 ; https://arxiv.org/abs/2109.03379 ; https://arxiv.org/abs/2206.08026 (all cached: fiducial/learned/)
- Technique: Deep ChArUco — SuperPoint-style ChArUcoNet (16 corner IDs + dustbin per 8x8 cell) plus RefineNet (sub-pixel 8x upsampled heatmap on 24x24 crops), PnP. Ghost-DeblurGAN — lightweight GhostNet-backbone DeblurGAN run *before* an unmodified AprilTag 3 / ArUco detector on motion-blurred frames; releases the YorkTag sharp/blurred pair dataset. DeepFormableTag — jointly learned marker generator + detector (Detectron2-based localiser + deformation-aware decoder) for markers on deformed surfaces.
- Reported speed-up: Deep ChArUco (GTX 1080, 320x240 input; Table "Approx. fps"): ChArUcoNet + RefineNet 66.5 fps, ChArUcoNet + cornerSubPix 98.6, ChArUcoNet + NoRefine 100.7, OpenCV + cornerSubPix 99.4, OpenCV + NoRefine 101.5 — i.e. the network front end on a desktop GPU only *matches* CPU OpenCV. Ghost-DeblurGAN-v4: 37 ms per frame on GPU (Quadro RTX-class) at GoPro-dataset size (DeblurGAN-v2 60 ms). DeepFormableTag: decodes 36-bit markers "at 29 fps" (Titan RTX-class GPU).
- Accuracy / determinism impact: Deep ChArUco: 97.4% vs 68.8% (OpenCV) of poses under a 3 px reprojection threshold across 26,000 low-light/blur frames. Ghost-DeblurGAN on YorkTag (Table II, garbled extraction): sharp 9,761 markers (100%), blurred 3,123 (31.99%); the two deblurred rows are 6,118 (62.68%) and 5,769 (59.10%) — assignment of these two numbers to Ghost-DeblurGAN vs HINet could not be recovered from the text. Either way, deblurring roughly doubles AprilTag 3 detections on blurred frames but still loses ~40% vs sharp.
- Applicability to vkapriltag: None as speed-ups; each costs tens of ms on a desktop GPU, versus vkapriltag's 3.76 ms full Mali phase. The recall lesson for FRC is that motion blur is the dominant recall killer (AprilTag 3 detects only ~32% of blurred markers here), and it is far cheaper to attack with exposure (Limelight: "Reducing exposure will always improve motion-blur resilience") than with a network. Out of scope for a bit-exact detector.

### Upstream maintainer guidance on decimation vs corner accuracy and tag-size priors — AprilRobotics/apriltag issues #96 and #351
- URL: https://github.com/AprilRobotics/apriltag/issues/96 ; https://github.com/AprilRobotics/apriltag/issues/351
- Technique: #96 asks for ArUco-style tag-size bounds to speed detection. Maintainer (mkrogius) answer: "The equivalent parameter would be the quad_decimate parameter. Set this higher ... at the cost of missing smaller tags if you set it above 2. This will not affect the accuracy of the tag corners since it decimates the image for only the detection part of the algorithm" — pointing to the AprilTag 3 paper; and: downsampling the image yourself and keeping quad_decimate = 2 "could be even slightly faster, at the cost of slightly less precision in the corner locations". #351 (Orin, 1920x1080, one core at 100%, only two tags of interest): community suggests an external (possibly NN / HW-accelerated) ROI proposer feeding crops to AprilTag.
- Reported speed-up: none quantified.
- Accuracy / determinism impact: The claim "does not affect corner accuracy" holds only with `refine_edges` on (the default), which re-fits edges on the full-resolution image; the refinement search range is `quad_decimate + 1` px along the normal (apriltag.c line ~811), so very coarse decimation widens the search and can snap to the wrong edge in clutter — not quantified upstream.
- Applicability to vkapriltag: Upstream's own position is that **the tag-size prior should be expressed as decimation**, not as a candidate filter — which supports turning the working tree's `APRILTAG_VK_MIN_TAG_PX` (a min_cluster_pixels floor) into a *decimation recommendation* for callers (largest decimation such that the smallest expected tag stays above the measured detection floor in decimated px; the floor itself must be measured — 36h11 has width_at_border = 8 cells). Also confirms that ROI cropping is expected to be done by the caller (see #105). Both devices.
- Verification: [verified from primary source: GitHub API]

### OpenCV `cv::aruco::ArucoDetector` "useAruco3Detection" — OpenCV objdetect module (cached fiducial/cv/aruco_detector.cpp)
- URL: https://github.com/opencv/opencv/blob/4.x/modules/objdetect/src/aruco/aruco_detector.cpp (cached copy)
- Technique: What OpenCV actually adopted from ArUco3: only the *single-frame* size prior. `fxfy = minSideLengthCanonicalImg / (minSideLengthCanonicalImg + max(W,H) * minMarkerLengthRatioOriginalImg)` (paper Eq. 1), the grey image is resized by `fxfy` for segmentation/contours, an image pyramid is built for canonical-size bit extraction, and corners are upsampled level by level with `cornerSubPix` (forced on: "always turn on corner refinement in case of Aruco3, due to upsampling"; other refinement methods just scale by 1/fxfy, which the code comments "will lead to inaccurate detections!"). The temporal parts (tau_i from the previous frame's smallest marker, Otsu-on-markers global threshold, random-threshold search) are **not** implemented; the caller must set `minMarkerLengthRatioOriginalImg` per frame if it wants ArUco3's video behaviour.
- Reported speed-up: none in code; see ArUco3 entry.
- Accuracy / determinism impact: Deterministic per call. Accuracy depends on subpixel upsampling; the comment documents that without it the upscaled corners are inaccurate.
- Applicability to vkapriltag: The mainstream library shipped the ArUco3 idea as a **stateless per-call knob with the policy left to the caller** — the same split proposed for vkapriltag (per-frame `(crop, decimation)` API, policy in PhotonVision). And OpenCV's warning mirrors AprilTag's: coarse detection is only acceptable with a full-resolution corner refinement step, which vkapriltag already has (`refine_edges` in the CPU tail). Both devices.

## Conclusions

Baseline: Mali-G610 GPU phase 3.76 ms + ~1.2 ms CPU tail at 1280x800 decimation 2 (FramePipeline 3.52 ms/frame); RX 9060 XT 0.66 ms GPU. The in-tree cost model on Mali is GPU ~= 560 us fixed + 3.3 us per 1k source pixels (86% of it scales with pixels). "Exact" below means bit-identical to libapriltag on the same input and decimation. For ROI modes it means bit-identical *per detected tag* to the full-frame run.

The main finding of this category: no published *algorithmic* change to the AprilTag 2/3 pipeline makes a single full-frame detection faster without changing its output. vkapriltag already has every trick in the AprilTag 3 paper. Edge-based, circle-based and learned alternatives are all slower. The real levers are the ones that **do less work per frame**: fewer pixels via ROIs, and coarser decimation. Both can be made exact per tag, so what remains is a recall trade-off, controlled by a caller-side policy.

### Ranked ideas

**1. ROIs predicted from the field map, with a full-frame fallback in the same frame (in-tree C1, made safe for FRC and exact per tag).** Recall risk only.
- **What:**
  - Project every field tag (known layout) from the last camera pose, not just last frame's detections (EagleEye). This catches a tag entering the view.
  - Use axis-aligned crops, with the origin aligned to 4 × decimation source px, and at least one threshold tile of margin plus room for motion.
  - Emit boundary points in full-frame integer coordinates (push-constant origin), so the moments and line fits are the same sums as a full-frame run. The CPU tail already samples the full image for decode and `refine_edges`.
  - If all ROIs come back empty, run the full frame in the same frame. Also run the full frame every Nth frame.
  - Pack the ROIs into one fixed-size atlas separated by constant gutters at least 2 tiles wide. Constant gutters threshold to 127, which never joins. The whole thing then runs in one dispatch chain and pays the 560 us fixed cost once.
- **Why it is exact:** traced in upstream code (ROI-exactness entry). Tile-anchored threshold, point-sampled decimation, final sort, and a dedup that breaks ties by corner coordinates. Rectifying warps are *not* exact: EagleEye's warped crops moved corners by up to 0.334 px and raised position noise by about 20%.
- **Uplift:** Mali about 2–3x on tracked frames. By the cost model, one or two 400x400 ROIs cost about 1.1–1.6 ms, against 3.76 ms for the full frame. EagleEye measured ROI-only frames about 6x cheaper than full-frame frames on a Pi 5 CPU (3.48 vs 20.6 ms). Worst case is ROI plus full frame on a frame where a track is lost. RDNA gains little, because fixed costs dominate its 0.66 ms.
- **Risks:**
  - A wrong pose, or a tag not in the layout, is found only on fallback or periodic frames.
  - A quiet zone broken inside the margin can split a component.
- **Bound it cheaply:**
  - (a) Exactness, CPU only: run upstream libapriltag on aligned crops of the PGM corpus and diff against the full-frame detections.
  - (b) Uplift and recall: replay EagleEye's public 7-clip 1280x800 synthetic dataset and record the ROI area fraction and how often fallback runs.

**2. Choose decimation per frame and per ROI (ArUco3 tau rule, Limelight `fiducial_downscale_set`, EagleEye's larger decimation for big ROIs).** Recall risk, plus small accuracy risk above decimation 2.
- **Uplift:** measured in-tree, decimation 4 is 2.1x faster than decimation 2 on the Pi (candidate quads fall from 75 to 17). It composes with idea 1: large near-tag ROIs can use decimation 3–4.
- **Evidence it is weaker in practice than in theory:**
  - EagleEye saw little gain from adaptive over static decimation.
  - ArUco3's rule misses a new small tag while a large one is being tracked.
- **Accuracy:** upstream and Limelight both say corners are unaffected because `refine_edges` refits at full resolution. Its search range grows as decimation + 1 px, and the effect at 3–4 is unquantified.
- **Upstream (#96):** a tag-size prior is best expressed as decimation. So the working tree's `APRILTAG_VK_MIN_TAG_PX` (a candidate floor) is worth more as a decimation recommendation.
- **Bound it cheaply:** sweep decimation 2/3/4 on the Orange Pi with PhotonVision's parameters (min_cluster_pixels 5, not upstream's 24). Record recall per tag size, and pose error against ground truth from FMAC renders.

**3. API shape: per-frame `(crop list, decimation)` in; the policy stays in the caller.** This is not a speed-up by itself. It is what lets 1 and 2 ship without touching the correctness gate: vkapriltag stays bit-identical to libapriltag for each (crop, decimation). OpenCV shipped ArUco3 the same way, as a stateless size knob. Limelight exposes crop and downscale over NetworkTables. Device: both.

**4. Indirect dispatch over only the non-flat 4x4 tiles (ChromaTag's sparse seeding, made exact).** Exact.
- **Uplift:** a few % of Mali GPU time at most, because flat 127 tiles are already cheap.
- **Bound it cheaply:** measure the fraction of all-127 tiles on real FRC frames. Drop the idea if it is under 30%.

**5. Early rejection before `fit_quad` / decode (ArUco Nano's revisit ratio, LFTag's cascade, in-tree C4).** Exact only if every test is provably a subset of upstream's own later rejections; otherwise recall risk.
- **Uplift:** capped by the ~1.2 ms CPU tail, which FramePipeline already hides. It helps the serial (latency) path only.
- **Bound it cheaply:** count per-stage rejections on real candidates, using LFTag's Table II as the template.

**6. Accuracy, not speed: optional analytic step-edge refinement** (Kallwies 2020: median corner error 0.017 vs 0.17 px). AprilTag 3 is weakest on axis-aligned tags, which is the FRC case. It would run Gauss-Newton with an analytic Jacobian on the few accepted tags, opt-in only. FMAC also reports a systematic half-pixel (0.62 mm) bias in AprilTag 3.4.5 that vkapriltag inherits by design. Don't mistake it for a GPU bug.

### Rejected by evidence
- **Learned detectors** (YoloTag, DeepTag, E2ETag, DeepArUco++, Deep ChArUco, DeepFormableTag, Ghost-DeblurGAN pre-filter): at best they match CPU detectors on desktop GPUs, and are usually slower. Corners are about 3x worse. On RKNN, YOLOv8n single-core 640x640 inference alone takes about 13.6 ms, against 3.76 ms for the whole Mali GPU phase, so it is not viable even as an ROI proposer.
- **Edge, gradient and voting front ends:**
  - AprilTag 1 is about 18x slower than AprilTag 2.
  - STag spends 80% of its time on edge extraction.
  - CCTag reaches only 11 fps on a GTX 980 Ti.
- **Optical-flow (KLT) tracking between detections** (Chilitags): the corners are not ID-verified and not exact, and it cannot find new tags.
- **Global threshold** (ArUco3), and colour, topological or circular markers (ChromaTag, TopoTag, LFTag, WhyCon, STag, CCTag): incompatible with FRC's 36h11 tags, or they lose lighting robustness.
- **Changing tag family:** the field is fixed 36h11, which is nearly free of false positives even at max hamming 2 (LFTag).
- **Rectifying (perspective-warped) ROI crops:** they cost accuracy (EagleEye) and break exactness.
