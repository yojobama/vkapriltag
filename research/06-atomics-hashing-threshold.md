## In-tree baseline (what the stages do today)

Read from `apriltags_vulkan/library/shaders/` and `OPTIMIZATION_NOTES.md` (third pass items 3, 6).

- `hash_group.comp`: one invocation per boundary point (~65k at dec 2, ~190k at dec 1). Linear probing, murmur-style 64->32 mix of (rep0, rep1), table = NextPow2(max_raw_blobs) = 65536 slots (256 KB) for ~400-1300 distinct keys, so load factor is ~1-2% and chains are ~1 probe. Slot holds `owner+1` (point index); insert is a single `atomicCompSwap(0 -> i+1)`, loser dereferences `keys[prev-1]` (written by an earlier barriered dispatch) and compares. Winner does `atomicAdd(raw_blob_counter)` to assign a dense id. `max_probes=128`, overflow counted in `drop_counter`. Key point for this category: with ~170 points per key, **the per-point cost is a plain load of a hot slot + a dependent 8-byte load of `keys[owner]`**, not a CAS - only one CAS per distinct key succeeds, and the rest only CAS if they saw 0 (a short race window at first touch).
- Dense id order is `atomicAdd` order => **scheduling-dependent** raw blob numbering; the pipeline is still bit-identical because nothing downstream depends on id order (select_blobs/scan/sort are order-independent by construction - worth re-checking whenever a change touches this).
- `reduce_extents_hash*.comp`: up to 8 atomics per point (4 min/max read-guarded, count+pxgx packed into one int64 atomic where available, gx/gy zero-guarded), privatized K=8 by `gl_WorkGroupID.x & 7` for bi < 4096, folded by `merge_extents.comp`. Mali measured: K=2 -13.1%, K=4 -18.5%, K=8 -20.3% GPU total; int64 packing -12 to -13% of span (0.252 -> 0.221 ms). Bound with plain stores: 0.434 -> 0.062 ms, so after the fixes ~0.16 ms of span is still atomic cost. `extents` is 1.01x across a 4x DRAM clock sweep: atomic/latency bound.
- `uf_final.comp`: saturating per-root counter; plain read, skip once `>= min_blob_pixels`, else atomicAdd. Exact predicate proof in-file. Scalar+guard beat subgroup aggregation 3x (MX230) and 3.5x (RX 9060 XT); aggregation deleted.
- `block_minmax` / `block_filter` / `threshold`: AprilTag's 4x4 block min/max, 3x3 neighbourhood min/max on the block grid, then per-pixel `127` if `max-min < min_white_black_diff` else `>` midpoint. Fusions measured +5.4..+7.8% on Mali and deleted; separable 3x3 bounded as unable to win (whole 3x3 gather 0.015-0.030 ms). `threshold` span is ~4% of the Mali frame, bandwidth ratio 1.34x.
- Subgroup reduce-by-key on Mali: `extents` 0.91 -> 6.04 ms (6.6x worse). Ballot-based anything is off the table on Mali.

### A Dynamic Hash Table for the GPU (SlabHash) — Ashkiani, Farach-Colton, Owens (UC Davis / Rutgers), IPDPS 2018 (arXiv 1710.11246)
- URL: https://arxiv.org/abs/1710.11246 (cached `ccl/hash/slabhash.txt`)
- Technique: Chained hash table whose nodes ("slabs") are 32 words = one warp width, so one coalesced load reads a whole node and a single `ballot` finds the empty/matching lane. "Warp-cooperative work sharing" (WCWS): the warp ballots its active lanes, elects one (`__ffs`), shuffles that lane's key to all lanes, and the whole warp processes that one operation, then repeats. REPLACE (unique-key insert) is a CAS into the lane found by `ffs(ballot(read==EMPTY || read==myKey))`. Uses its own warp-synchronous allocator (SlabAlloc, 600 M allocations/s, 37x Halloc).
- Reported speed-up: Tesla K40c, up to 512 M updates/s and 937 M queries/s; comparable to CUDPP cuckoo (CUDPP 1.19x faster search at 65% utilization in their harmonic-mean comparison; CUDPP 2.04x faster build per the text). [numbers read from cached text]
- Accuracy / determinism impact: lock-free; which lane/slot wins is scheduling-dependent, as in any concurrent insert.
- Applicability to vkapriltag: **Not applicable on Mali.** The whole design is built on ballot+shuffle per operation - exactly the construct measured 6.6x slower in `reduce_extents_hash_subgroup` on the G610 - plus a dynamic allocator the pipeline doesn't need (key count is bounded by max_raw_blobs). Two ideas transfer conceptually: (1) its REPLACE shows the standard "unique-key insert = CAS on EMPTY, else compare" which hash_group already does per-thread; (2) SlabHash is designed for *high load factors*, which is the opposite of vkapriltag's regime (1-2% load). On RDNA the WCWS pattern would only help if probe chains were long; they are ~1.

### WarpCore: A Library for fast Hash Tables on GPUs — Jünger, Kobus, Müller, Hundt, Xu, Liu, Schmidt (JGU Mainz / NVIDIA), HiPC 2020 (arXiv 2009.07914)
- URL: https://arxiv.org/abs/2009.07914 (cached `ccl/hash/warpcore.txt`)
- Technique: Open addressing with "Cooperative Probing Scheme" (COPS): an outer double-hashing sequence picks a window, and a cooperative group (CG) of g threads (sub-warp tile, 1..32) loads g adjacent slots at once and votes for a match/empty lane; insert is one CAS on the key slot (packed key+value CAS where it fits so no separate value store). Discusses LP vs QP vs DH: LP is cache-efficient but primary clustering gives high probe-length variance near capacity; DH avoids clustering at the cost of more cache misses. SoA vs AoS layouts; multi-value variants (bucket lists).
- Reported speed-up: single GV100, up to 1.6 G inserts/s and 4.3 G retrievals/s; inserts 3.95x cuDPP and 1.6x cuDF at load 0.97 / 0.8; "for relatively low densities, SlabHash's performance is on par with WC", WC pulls ahead above ~70% load. Retrieval 8.76x cuDF (0.8), 1.64x cuDPP (0.9), 2.39x SlabHash (0.9). cuDF's LP "handles high key multiplicities worse" (primary clustering when many identical keys share an initial position - multi-value case).
- Accuracy / determinism impact: slot placement is scheduling-dependent for colliding keys; the set of (key -> slot) is deterministic only if there are no collisions.
- Applicability to vkapriltag: The paper's own data says the probing-scheme choice matters **only at high load** (>70%); at low density all schemes are on par. vkapriltag runs at ~1-2% load (65536 slots, 400-1300 keys), so LP is already optimal - DH or COPS would only add hash work and cache misses. The CG-cooperative window needs subgroup votes (off the table on Mali; pointless on RDNA at chain length ~1). One transferable detail: WC packs key+value so a *single CAS* both claims and publishes. vkapriltag goes further (the key lives in `keys[owner]`, published by an earlier dispatch), which is what makes it spin-free - keep that. Nothing to adopt.
- Verification: [verified from primary source] (cached PDF text)

### WarpSpeed: A High-Performance Library for Concurrent GPU Hash Tables — McCoy, Pandey (Northeastern), SIAM ACDA 2026 (arXiv 2509.16407)
- URL: https://arxiv.org/abs/2509.16407 , code https://github.com/saltsystemslab/warpSpeed (cached `ccl/hash/warpspeed.txt`)
- Technique: Eight NVIDIA designs (Iceberg, power-of-two-choice P2HT, 3-way bucketed cuckoo, double hashing, chaining, plus fingerprint-metadata variants) under one benchmark. Central argument: **stability** (a key never moves after insertion) is what allows lock-free queries and compound ops (upsert); cuckoo is unstable, so concurrent cuckoo needs per-bucket locks. They show an adversarial benchmark in which atomics-only designs (SlabHash) produce duplicate keys. Lock-free queries via a reservation marker CAS then a 128-bit store-release of key+value. Fingerprint metadata cuts cache-line probes because every concurrent probe needs acquire semantics (20-50% overhead per bucket load).
- Reported speed-up: IcebergHT/P2HT/DoubleHT fastest insert (21%+ over alternatives); DoubleHT fastest query (up to 20%); concurrency costs 1-25% vs bulk-synchronous; best vs worst tile/bucket configuration >1300%; tuned bucketed cuckoo 2.4-3.8x over BCHT; "every atomic operation incurs a performance hit of ~50 million operations per second". NVIDIA only.
- Accuracy / determinism impact: its locking designs are deterministic in content (no duplicates) but rely on spin locks, i.e. on independent forward progress.
- Applicability to vkapriltag: Confirms the two design choices in `hash_group.comp` from the theory side: (1) **no cuckoo / Robin Hood** - both move keys (unstable) and need either locks (spin: not allowed without Vulkan forward-progress guarantees) or multi-word atomic swaps; with owner-index slots a displaced key would also invalidate other threads' `point_slot[]`. (2) vkapriltag sidesteps the acquire-load cost WarpSpeed pays on every probe, because the key is published in a *previous dispatch* and the slot only carries an index; the relaxed load of `hash_owner[h]` is safe (stale 0 -> CAS returns the truth; non-zero -> key already visible). The WarpSpeed "atomics-only duplicates" failure mode needs deletions or moves, which vkapriltag has neither of. Nothing to adopt; this is the strongest published argument for keeping linear probing + single CAS.

### Better GPU Hash Tables (BGHT) — Awad, Ashkiani, Porumbescu, Farach-Colton, Owens (UC Davis / Google / Rutgers), APOCS 2023 (arXiv 2108.07232)
- URL: https://arxiv.org/abs/2108.07232 , code https://github.com/owensgroup/BGHT (cached `ccl/hash/bght.txt`)
- Technique: Static (build-once) bucketed tables: bucketed cuckoo with 3 hash functions (BCHT), bucketed power-of-two-choices (BP2HT), iceberg (IHT). Bucket = one 128-byte cache line (b=16 x 8-byte pairs) probed cooperatively by a tile. Cuckoo insert is a chain of `atomicExch` displacements, serial within a thread, bounded by a max-exchange count; failure => rebuild. Argument: once a bucket is a cache line, "probe count" = cache lines touched, and larger buckets trade cheap in-line compares for fewer lines.
- Reported speed-up: BCHT (b=16, 3 hashes) reaches load factor up to 0.98, avg 1.43 probes/insert at 0.99, <=1.39 / 2.8 avg probes for positive/negative queries; highest query and insert throughput of the designs. IHT stable but <=0.82 load (b=16); BP2HT stable, ~0.82. Comparisons vs WarpCore / DyCuckoo cited in text (e.g. {2.3x, 1.6x} over WarpCore at some windows). NVIDIA only.
- Accuracy / determinism impact: cuckoo placement depends on exchange order (non-deterministic layout); build can fail (>=99% success guaranteed by their parameter choices) and require a rebuild - a rebuild loop is a host-visible, frame-dependent path.
- Applicability to vkapriltag: **Reject cuckoo (bucketed or not) for hash_group.** (a) It is a static bulk-build design; hash_group interleaves find-or-insert for ~170 duplicates per key, which cuckoo handles badly (a thread that displaced a key must re-probe; duplicates can race into two buckets unless locked - the WarpSpeed finding). (b) Displacement moves keys, which breaks the owner-index/point_slot scheme (a point's recorded slot must be final). (c) Failure => rebuild is not spin-free in the Vulkan sense. The only transferable idea is "bucket = cache line": on Mali (64-byte lines) a probe that misses could scan 16 x 4-byte owner slots in one line - but at 1-2% load the first slot matches ~98% of the time, so this buys nothing. BGHT's own recommendation matrix is about memory-constrained, high-load tables; vkapriltag is the opposite corner (tiny key set, huge table).

### Optimizing GPU-accelerated Group-By and Aggregation — Karnagel (TU Dresden), Mueller, Lohman (IBM Almaden), ADMS@VLDB 2015
- URL: http://www.adms-conf.org/2015/gpu-optimizer-camera-ready.pdf (cached `ccl/hash/karnagel.txt`)
- Technique: Hash-based GROUP BY with open addressing + linear probing, aggregates updated in place with atomics, one global atomicInc to number new groups (the same shape as `hash_group` + `reduce_extents_hash`). Profiles runtime vs number of groups and finds five regimes. **Region I (few groups): contention.** Their explanation: on Kepler+ atomics execute in ALUs at the L2, routed by address; "updates to the same hash bucket, *or to buckets that are located on the same cache line*, are sent to the same ALU", so with 8-byte buckets 16 groups share one 128-byte line and one ALU. Region II: spiky runtime from hash-to-bucket mapping collisions (FNV-1a + modulo on compact key domains; variance >3 orders of magnitude; Murmur3 fixes it). Fixes for few groups: block-private tables in shared memory, or thread-private tables in device memory, merged at the end. Also compares against CUB radix sort + ReduceByKey.
- Reported speed-up: GTX Titan (Kepler), 335M rows: parameter tuning up to 4.4x; block-private shared-memory tables flatten runtime to the PCIe floor (0.11 s) from 6 groups up; thread-private tables best at <=6 groups. **Hash-based beats sort-based below ~200,000 groups** (single pass vs multiple radix passes), sort wins once the table exceeds L2.
- Accuracy / determinism impact: group numbering by global atomicInc is order-dependent; sums are integer so exact.
- Applicability to vkapriltag: (1) Validates the hash-vs-sort decision (400-1300 groups, far below 200k; in-tree measured sort+group 10.90 -> 3.06 ms). (2) The **same-cache-line-same-atomic-unit** mechanism is directly relevant to `reduce_extents_hash`: `MinMaxExtentsGpu` is 32 bytes, so blob `bi` and `bi^1` share one 64-byte line in *every* copy (copy 0 at `bi`, copy c at `max_raw_blobs + (c-1)*4096 + bi`). If Mali/RDNA serialize atomics per line (likely for Mali's L2-side atomics - unverified), padding the struct to 64 bytes, or interleaving so adjacent lines hold different copies, halves per-line atomic traffic at no algorithmic cost; bit-identical. Cost: extents buffer 2x (~1 MiB -> ~2 MiB replicated region) and `select_blobs`/host readback stride changes (or pad only the private copies and keep copy 0 at 32 bytes). Bound it cheaply: map copy c of blob bi to `2*bi` spacing (skip odd entries) in the private region only and A/B the `extents` span. (3) Their murmur-vs-FNV finding supports the existing murmur finalizer in hash_group; compact key domains (dense small ids - exactly vkapriltag's rep0/rep1) are the bad case for weak mixes. (4) Their block-private-table fix needs real shared memory - not on Mali; K=8 device-memory privatization is the Mali analogue and is shipped.
- Verification: [verified from primary source] (cached text; the per-line-ALU explanation is the authors' hypothesis for Kepler, not a vendor statement)

### Data-Parallel Hashing Techniques for GPU Architectures (survey) — Lessley (U. Oregon), arXiv 1807.04345, 2018
- URL: https://arxiv.org/abs/1807.04345 (cached `ccl/hash/lessley.txt`)
- Technique: Survey of GPU open addressing (linear, cuckoo, double, multi-level bounded linear, Robin Hood), perfect hashing, spatial hashing and chaining, with a use-case recommendation table. Relevant items: (a) Karnagel's group-by guidance restated - ideal table fits in L2 with load < 50%, higher loads cause contention and long probe sequences; (b) **CoherentHash (García et al., Robin Hood)**: a *spatially coherent* hash function makes neighbouring threads with neighbouring keys probe neighbouring slots, so probes coalesce; big wins on spatially ordered keys, "little to no benefit" on random order; (c) Robin Hood evicts the younger key (needs eviction = key movement) and reconstructs the table past a max age (15 in García); (d) HashFight: iterative winner-takes-all without hardware atomics, rebuilding a smaller table per round.
- Reported speed-up: survey - no new numbers of its own; CoherentHash reported faster than Alcantara's 4-hash cuckoo on coherent data and failure-free above 0.7 load (per the survey's summary).
- Accuracy / determinism impact: Robin Hood / cuckoo layouts depend on insertion order; HashFight's winner is whoever wrote last (order-dependent).
- Applicability to vkapriltag: The survey's taxonomy puts vkapriltag's case ("duplicate insertions", integer keys, low occupancy, find-or-insert) squarely in simple open addressing. Robin Hood is out for the same reason as cuckoo (moves keys => breaks owner-index slots and spin-freedom; reconstruction on overflow). The one idea worth noting is **coherence**: boundary points are appended by `blob_diff` roughly in raster/workgroup order, so consecutive points usually share a key and hit the *same* slot - the current murmur mix is irrelevant to coherence there because equal keys already coalesce; making different-but-nearby keys land in nearby slots would only matter if chains were long. HashFight-style atomic-free rounds need barriers between rounds (dispatches on Vulkan, 2.6-18.7 us each on Mali) - strictly worse than one CAS per distinct key. Nothing to adopt.

### GPU Atomic Performance Modeling with Microbenchmarks — Devon McKee, Tyler Sorensen et al. (UC Santa Cruz), Vulkanised 2024
- URL: https://vulkan.org/user/pages/09.events/vulkanised-2024/vulkanised-2024-devon-mckee.pdf (cached `ccl/hash/mckee.txt` / `mckee_vulkanised2024.pdf`); demo devon.engineering/epiphron-web
- Technique: A Vulkan microbenchmark suite (OpenCL kernels -> SPIR-V via clspv) sweeping **contention** (threads per atomic location) x **padding** (spacing between locations) for three access patterns (contiguous: chunked within warps; cross-warp: strided; random), producing throughput heatmaps per device.
- Reported speed-up (slide-level, no absolute numbers in the text): Intel discrete - peak at contention=1, padding=1, degrades to <5% of peak in some cells. **AMD discrete - peak at contention=4, padding=1**, degrades to ~1% of peak. NVIDIA - peak past contention=32 (intra-warp coalescing of same-address atomics), slow region ~4% of peak. Random access: AMD peaks locally at 16 atomic locations, rises again past 64; "bit packing until 16 atomics used greatly improves throughput"; NVIDIA throughput falls as soon as locations > 1. Mobile/Apple listed as future work - **no Mali/Adreno data in this talk**.
- Accuracy / determinism impact: n/a (measurement methodology).
- Applicability to vkapriltag: Two direct consequences. (1) GPU atomic cost is **not** CPU-like: padding=1 (adjacent locations) is the peak on AMD and Intel, i.e. *padding atomics to separate cache lines is not automatically a win on GPUs* - this cuts against the Karnagel-derived "pad MinMaxExtentsGpu to 64 B" idea, so that idea must be measured on Mali, not assumed. (2) The suite is Vulkan and runs anywhere; running it (or a 50-line equivalent) on the G610 would give the missing Mali curve - throughput vs contention (1..256) and vs spacing (4 B..128 B) - which is exactly what's needed to choose K (privatization factor), struct padding and copy interleave for `reduce_extents_hash`, and to predict whether `uf_final`'s guard is still worth it at decimation 1. Cheapest high-value experiment in this category.

### Are Your GPU Atomics Secretly Contending? — Maucher, Djerfi, Kittner, Werling, Bellosa (KIT), PLOS '25 (SOSP workshop), Oct 2025
- URL: https://doi.org/10.1145/3764860.3768338 , suite https://github.com/KIT-OSGroup/GPUAtomicContention (cached `ccl/hash/plos25.txt`)
- Technique: Precise microbenchmarks of device-scope atomicAdd on AMD RX 6950 XT (RDNA2), RX 7900 XTX (RDNA3), RTX A4500, RTX 4070: uncontended baseline, threads-per-warp scaling on one variable, and **cross-contention between distinct variables vs their memory stride**, with one variable per warp or several per warp.
- Reported speed-up / findings: uncontended atomic 2.4-3.5 ns NVIDIA, ~6.5-7 ns AMD (128 reps; 85-100 ns at 1024 reps - AMD "self-contention"). Up to 32 same-address requests are absorbed flat by the atomic unit on both vendors (so warp-aggregating a lightly contended counter "may not be worth" it - the same thing vkapriltag measured for `uf_final`/`blob_diff`). **Cross-contention: 128 B stride behaves like 0-64 B; contention drops only at >= 256 B** ("two atomic variables should be at least 256 B apart"). **On AMD, contention rises again at a 4096 B stride**: the authors infer the low 12 address bits select the atomic unit, so power-of-two strides pile every variable onto one unit; non-power-of-two strides fix it (verified by rerun). Adjacent variables (4-8 B stride) accessed by different lanes of *one* warp are parallelized by the unit - fast.
- Accuracy / determinism impact: n/a - layout only; any re-layout of privatized copies is bit-identical because min/max/sum folds are exact and order-free.
- Applicability to vkapriltag: **Direct hit on the extents privatization layout.** `ExtentsSlot` places copy c of blob bi at element `max_raw_blobs + (c-1)*4096 + bi` with a 32-byte struct and `max_raw_blobs = 65536`, i.e. byte offsets `2 MiB + (c-1)*128 KiB + 32*bi`: **all 8 copies of a blob are exactly 128 KiB apart, identical in their low 17 address bits.** Under the paper's AMD model they all land on the same atomic unit, so the replication buys less same-*unit* relief than it should; on Mali the question is whether L2-slice selection hashes high bits (unknown - see Arm entries). It also fits an otherwise odd in-tree result: Mali K=8 -20.3%, K=16 -20.0%, K=32 -20.6% - a hard plateau that same-slice aliasing would produce. **Idea (bit-identical, ~3 lines):** skew the copy stride off a power of two and off 256 B multiples of each other, e.g. `max_raw_blobs + (c-1)*(4096 + 9) + bi` (9 x 32 B = 288 B skew per copy), or make the private copies of one blob *adjacent at 256 B spacing* (`bi*8*... `) - two variants, A/B on Mali with K=8 and K=16. Also: 2 blobs share each 64 B line and 8 blobs share each 256 B "contention granule" in every copy, so padding the private copies to 64 B (or 256 B) per blob is the second axis to sweep. RDNA takes the unprivatized subgroup path, so this is a Mali (and scalar-fallback) item. Bound: one build with the skew, `extents` span ABBA; if flat, the aliasing theory is dead on Mali.
- Verification: [verified from primary source] (cached text; measured on RDNA2/3 + Ampere/Ada only - Mali behaviour is extrapolation)

### Arm GPU Best Practices Developer Guide, rev 3.4 (Issue 10), §10.13 Atomics and §9.3 Shared memory — Arm Ltd, 2025-01-31
- URL: https://developer.arm.com/documentation/101897/0304 (cached `ccl/hash/arm_bp.txt`, same as `mali/bp34.txt`)
- Technique: Arm's stated mechanism for Mali atomics: "Atomics are efficient when a shader core controls the necessary cache line in its L1." Contention means atomics from *different shader cores* hitting the same cache line, which "requires data coherency snooping through L2 cache, which is computationally expensive". Recommendations: spread contention by keeping atomics local to one shader core; **space atomics 64 bytes apart** (one per cache line); accumulate into a shared-memory atomic and push one global atomic per workgroup; in OpenCL use `cl_arm_get_core_id` for **explicit per-shader-core atomic variables**; "if better solutions that use multiple passes are available, then do not use atomics". Debug with the L1 snoop performance counters. §9.3: Mali has no dedicated shared memory (backed by the memory system), keep it small, don't copy global->shared.
- Reported speed-up: none (guidance only).
- Accuracy / determinism impact: per-core privatization with an exact fold is bit-identical; which core a workgroup runs on is scheduling-dependent but irrelevant to the folded result.
- Applicability to vkapriltag: **This reframes the extents privatization on Mali.** vkapriltag picks the copy by `gl_WorkGroupID.x & 7`; workgroups are spread over the G610's 4 cores, so every copy's lines are still written by all 4 cores over the dispatch and keep migrating between L1s - privatization by workgroup reduces *same-address* serialization, not *line ownership ping-pong*, which is what Arm names as the cost. The Arm-prescribed fix is **copy = shader core id**: `VK_ARM_shader_core_builtins` (present in both libmali g24p0 and g29p1 extension lists in the cache) exposes `gl_CoreIDARM` / `gl_CoreMaxIDARM`; with one copy per core, a copy's lines stay resident in one core's L1 and atomics become core-local. The survey's line "K=4 privatization already measured, no gain expected" conflates K=4-by-workgroup with K=4-by-core - they are different mechanisms, so the extension deserves a measurement, not a dismissal. Combine with the Arm 64-byte spacing: `MinMaxExtentsGpu` is 32 B, two blobs per line; pad private copies to 64 B. Also worth checking with the snoop counters (Streamline / `libGPUCounters`) before building - a high L1 snoop count in `reduce_extents_hash` confirms the mechanism. Applies equally to `uf_final`'s `blob_size[root]` counters (a large blob's counter line migrates between cores until saturation) and to `blob_diff`'s append counter / `raw_blob_counter`. Vendor extension => must stay optional with the current path as fallback (the tree's "core 1.1, zero optional features" posture already has int64 atomics as a precedent).
- Verification: [verified from primary source] (Arm document text); the per-core payoff is **unmeasured** - Arm gives no numbers.

### Memory-efficient and fast implementation of local adaptive binarization methods — Chungkwong Chan (Sun Yat-Sen U.), arXiv 1905.13038, 2019
- URL: https://arxiv.org/abs/1905.13038 , code https://github.com/chungkwong/binarizer (cached `ccl/hash/binarize1905.txt`)
- Technique: Sauvola/Niblack-family thresholds `t = m(1 + k(s/R - 1))` need per-pixel window mean and std. Instead of two integral images (16HW bytes, 64-bit entries at high resolution), keep running column sums C_j, D_j (sum, sum of squares) and slide the window recursively: O(HW) time independent of window size, ~6 min{H,W} bytes of auxiliary state. Generalizes to quantile-based methods via sliding histograms (O(HW max{h,w})).
- Reported speed-up: CPU, ICDAR 2013 DIBCO set: ~30% faster than the integral-image Sauvola, ~6x slower than global Otsu; identical output across the three Sauvola implementations. Cites a GPU Sauvola (Chen et al.) without numbers.
- Accuracy / determinism impact: exact (integer sums).
- Applicability to vkapriltag: **None for the algorithm** - the correctness gate is bit-identity with libapriltag's 4x4-block min/max + 3x3 block-grid dilation + midpoint test, so Sauvola/Niblack/Bradley would change which pixels are 0/255/127 and fail the gate outright. The implementation lesson (recursive sliding sums instead of materialized integral images; state per column, not per pixel) is a serial-CPU trick; on a GPU the equivalent is exactly what vkapriltag already does - AprilTag's block grid *is* a 16x-downsampled statistic, and the 3x3 dilation runs on the 16x-smaller grid. ### In-tree analysis: packing gx_sum/gy_sum into one int64 atomic — this pass (source: `reduce_extents_hash_body.glsl`, `common.glsl`, `merge_extents.comp`, `select_blobs.comp`)
- URL: n/a (repo read)
- Technique: `gx_sum` and `gy_sum` sit at byte offsets 24/28 of the 32-byte `MinMaxExtentsGpu`, i.e. they already form one naturally aligned 64-bit word (u64 index `s*4+3`), exactly like the shipped `(count, pxgx)` pair at `s*4+2`. Today a point issues `atomicAdd(gx_sum)` if `gx != 0` and `atomicAdd(gy_sum)` if `gy != 0`: E/S points 1 atomic, SE/SW diagonal points 2. Packing both into one 64-bit `atomicAdd` makes it exactly 1 for every point. Signed halves carry into each other, so use a **bias**: add `(uint64(gy + 1) << 32) | uint(gx + 1)` (each half gains 0..2 per point, so a half stays below `2*count < 2^32` and never carries); the stored fields become `gx_sum + count` and `gy_sum + count`. `merge_extents` folds them with its existing 32-bit adds unchanged (bias is linear, sums to the merged count); `select_blobs::hasReversedBorder` subtracts `e.count` from each before use. `gx_sum`/`gy_sum` have no other reader (grep: only init/merge/select/subgroup variant; host never reads them).
- Reported speed-up: none measured. Estimate: the atomics that survive the guards per point are ~1 (count+pxgx) + 1..2 (gx/gy) + rare min/max, so this removes the diagonal points' second atomic - ~0.25-0.5 of ~2.5 per point (depends on the E/S vs diagonal mix of boundary points, unmeasured). The analogous count+pxgx packing measured -12..-13% of the extents span on Mali.
- Accuracy / determinism impact: exact (integer, no carries by the bound above; the bias is removed exactly); bit-identical. Must be tied to the variant: the RDNA subgroup path stores unbiased sums, so `select_blobs` needs a spec constant / define matching the reduce variant (or give the subgroup path the same bias).
- Applicability to vkapriltag: **In-tree history: OPTIMIZATION_NOTES.md A8 rejected packing gx/gy into one *32-bit* atomic** (a raw blob can own up to 2,061,616 points at 1080p dec 2, so a biased field needs ~19-22 bits and two cannot share 32 bits) and noted "a 64-bit atomicAdd has the width but needs VK_KHR_shader_atomic_int64, which is not core"; A8-lite (zero-guards) shipped. The int64 variant has since shipped for (count, pxgx), so A8's stated blocker is gone on exactly the devices that take that variant; with 32-bit halves the bias bound is 2 x 2,061,616 < 2^22, far inside 2^32. Mali (int64 atomic path, which the G610 takes). Stacks with ideas 2-4 in Conclusions because it cuts atomic *issue count* - the mechanism the G610 counter guide says is "multi-cycle per thread" - rather than contention. Bound cheaply: count, on one captured frame, points with both gx and gy non-zero (a 5-line host tally over `compacted[]`); the fraction is the upper bound on atomics removed.

### frc971 NEON threshold (`frc/orin/neon_threshold.cc`, commit 922568c79 "Implement the threshold step in NEON") — Austin Schuh (FRC 971), 2025-02-17
- URL: cached clone `fiducial/RealtimeRoboticsGroup_aos/frc/orin/neon_threshold.cc`, `threshold.cc`, `threshold_test.cc`, `apriltag.cc` (flag `--use_neon`)
- Technique: CPU (ARM NEON) implementation of the *whole* AprilTag preprocessing - decimate-by-2 point sample (`vuzp1_u8` of every other byte), 4x4 block min/max on the decimated grid, 3x3 block dilation done **separably and fused**: pass 1 walks each block row, computes block min/max and immediately the *horizontal* 3-wide filtered min/max (delayed by one block pair), stored as packed `uint16` min|max; pass 2 does the vertical 3-tall filter and writes the 0/127/255 pixels 8 at a time. Two passes over the image, no intermediate full-size buffers. When enabled, the CUDA detector's threshold kernels are skipped and the CPU writes the decimated and thresholded images straight into unified memory before the GPU stream starts.
- Reported speed-up: commit message: "The GPU was too full, this moves it back to the CPU" and "a 3x speedup over the original aprilrobotics CPU code" (Orin; no absolute ms given in the commit; the code carries a TODO estimating 0.05 ms more from SIMD horizontal reductions). `threshold_test.cc` "Tests that the NEON threshold matches the CUDA one which we know is correct."
- Accuracy / determinism impact: exact integer min/max and compare; tested equal to the CUDA path, i.e. bit-identical by construction (same arithmetic as libapriltag's `threshold()` for this decimation).
- Applicability to vkapriltag: **New idea for the RK3588 target: CPU/NEON preprocessing offload.** vkapriltag on the Orange Pi is GPU-bound (GPU 3.76 ms vs CPU tail 1.23 ms; pipelined 3.52 ms/frame), and the RK3588 has 4 A76 + 4 A55 cores mostly idle while `FramePipeline` overlaps only one CPU tail with the GPU. With unified memory there is no copy: a spare A76 core writes `decimated` and `thresholded` directly into the host-visible buffers and the GPU command buffer starts at `uf_init`. Removes decimate + block_minmax + block_filter + threshold spans and their barriers from the GPU (the repo's `vkapriltag-optimization-ideas.md` B4 verdict records "the whole `decimate`+`threshold` stage is 0.86 ms of Mali's 2.59 ms labelling stage" - an older build, at decimation 1 by that doc's baseline config; at the deployed decimation 2 the share is smaller, ~4% of the frame for `threshold` alone; read the current spans from `APRILTAG_VK_TIMESTAMPS=1`), at the cost of one frame of added latency if run as a third pipeline stage (throughput-neutral otherwise). Also lets the GPU skip the full-resolution input read (the largest DRAM pass - though only ~15% of the Mali frame is DRAM-bound at all). Correctness: frc971's approach is exact; port its two-pass separable NEON code (MONO8/YUYV only, width%16, height%8 constraints, and hard-wired to decimation 2 - it loads every other row and `vuzp1`s every other byte; decimation 1/3/4 need their own inner loops). Risks: CPU memory bandwidth contention with the GPU (shared LPDDR), cache maintenance on non-coherent host-visible memory (need HOST_COHERENT or flush), and big.LITTLE placement (pin to A76, cf. rapidtag). Bound cheaply: time frc971's `ThresholdAndDecimate` on one A76 at 1280x800 (standalone, ~50 lines of harness) and compare with the sum of the four GPU preprocessing spans; worth building only if CPU time < GPU spans saved and the CPU core is free. Not relevant to RDNA (0.66 ms GPU, PCIe copy would dominate).

### In-tree analysis: hash_group probe path and table clear — this pass (source: `hash_group.comp`, `GpuDetector.cpp` l.400-414, PERFORMANCE.md §3a)
- URL: n/a (repo read)
- Technique: Per point today: coalesced `keys[i]` load -> murmur mix -> `hash_owner[h]` load (hot) -> **dependent** `keys[owner-1]` 8-byte load (hot: all ~170 points of a key share one owner) -> compare -> `point_slot[i]` store. Two ideas from the hash-table literature, both bit-identical:
  (a) **Key-in-slot with a 64-bit CAS** (WarpCore's packed key/value CAS): make the slot a `uint64` holding `(rep0, rep1)` itself; empty = 0 is a safe sentinel because a boundary key always has `rep0 != rep1`, so (0,0) cannot occur. Probe = one load + compare; insert = `atomicCompSwap(slot64, 0, key)`, winner still does the `raw_blob_counter` add and writes `slot_dense[h]`. Removes the dependent `keys[owner]` load and the owner index entirely (spin-freedom preserved - no thread reads another's later write). Cost: `hash_owner` 256 KB -> 512 KB, i.e. more `clear` traffic; needs int64 atomics (G610 and RDNA4 both have them; keep the 32-bit owner path as fallback).
  (b) **Skip the per-frame clear of `hash_owner`** with an epoch tag (store `epoch<<21 | owner+1`, treat a stale epoch as empty, CAS against the stale value read; full clear only on epoch wrap). Owner indices reach ~2.06 M (<2^21) at 1080p dec 2, leaving 11 bits of epoch.
- Reported speed-up: none measured. Bounds from in-tree data: `clear` is 0.048 ms at the deployment DMC clock (PERFORMANCE.md §3a) and covers `blob_size` (1 MB at 1280x800 dec 2) plus the 256 KB table, so (b) is worth <= ~0.01 ms and (a) *adds* ~0.01 ms of clear. (a)'s gain is one L1/L2-hit dependent load per point (~65k at dec 2, ~190k at dec 1); `hash_group` is not separately reported in the Mali tables I read (it sits inside "sort+group", 20% of the dec-1 frame in `vkapriltag-optimization-ideas.md`).
- Accuracy / determinism impact: none (same grouping; dense-id order is already scheduling-dependent and unconsumed).
- Applicability to vkapriltag: **Low priority, both devices.** Bound (a) with a deliberately incorrect build that skips the `keys[o] == k` check on probe 0 (accept the first slot) and read the `hash_group` span; build (a) only if that ceiling is >= ~0.03 ms. (b) is not worth it on the numbers. The literature (SlabHash/WarpCore/BGHT/WarpSpeed) offers nothing larger for a 1-2%-load, ~1-probe table.

### Specifying and Testing GPU Workgroup Progress Models — Sorensen, Salvador, Raval, Evrard, Wickerson, Martonosi, Donaldson, OOPSLA 2021 (arXiv 2109.06132)
- URL: https://arxiv.org/abs/2109.06132 (cached `ccl/scansort/progress2109.txt`)
- Technique: Formal progress models (OBE, HSA, LOBE) plus 483 synthesized litmus tests (mutex / spin-wait patterns between workgroups), run on 8 GPUs from 5 vendors via Vulkan/CUDA/Metal.
- Reported findings: "Vulkan and Metal say almost nothing about relative forward progress guarantees between workgroups". All tested GPUs support OBE (occupancy-bound execution - workgroups that have started keep being scheduled) and HSA; **Apple and ARM GPUs fail tests that the stronger LOBE model guarantees**, i.e. they do *not* even provide the intuitive "linear occupancy-bound" behaviour.
- Accuracy / determinism impact: n/a (liveness).
- Applicability to vkapriltag: The strongest external confirmation that the `hash_group` design (single CAS, loser reads a key published by an *earlier dispatch*, no waiting on another thread's later write) is the right one, and that any hash-table idea involving a spin lock, a reservation-then-publish handshake between invocations (WarpSpeed's lock-free queries wait on a store-release by the reserving thread), cuckoo displacement with locks, or a decoupled look-back without fallback is unsafe **specifically on Mali**. It also rules out "persistent-thread" work-stealing variants of `reduce_extents_hash` or `sort_points_local` on the target. The idea-list filter for this category is therefore: an in-dispatch protocol may *read* results of earlier dispatches and *CAS/atomic-RMW* shared words, but must never *wait* for another invocation of the same dispatch. The gx/gy packing, key-in-slot 64-bit CAS, and all extents layout ideas above satisfy it.

### In-tree analysis: keep ambiguous (127) pixels out of `blob_size` entirely — this pass (source: `uf_final.comp`, `label_pixels_body.glsl`, `uf_init.comp`, `GpuDetector.cpp` l.962-980, OPTIMIZATION_NOTES.md §3, PERFORMANCE.md §3a)
- URL: n/a (repo read)
- Technique: A 127 pixel never joins anything (`uf_init`: `join_left = (v != 127) && ...`; `uf_merge` likewise), so after convergence it is its own root, `r == i`, with true size 1. Today `uf_final` still does, for each of them, `parent[i]` load -> `blob_size[i]` load (0) -> `atomicAdd(blob_size[i], 1)`, and `label_pixels` loads `blob_size[i]` again to compute `label = (1 >= min) ? i+1 : 0`. With `min_cluster_pixels >= 2` (default 24; it is the value both shaders receive) that label is provably 0. So: in `uf_final`, read the threshold code and return early for 127; in `label_pixels` (which already reads the code via `THRESHOLDED_AT(i)`), set `label = 0` for 127 without touching `blob_size`. Guard with `min_cluster_pixels >= 2` on the host (otherwise keep the current path).
- Reported speed-up: none measured. Magnitude: OPTIMIZATION_NOTES.md §3 records 153,886 union-find roots in a 1080p dec-2 frame, "nearly a third of all decimated pixels - because it included every single-pixel speck and every ambiguous region"; those are exactly the pixels whose `blob_size` accesses are *streaming* (address = own index, no reuse) and hence the DRAM-proportional part of `uf_final` (2.66x across the DMC sweep) and `label_pixels` (3.12x). For each such pixel this replaces a 4-byte load + 4-byte atomic RMW (uf_final) and a 4-byte load (label_pixels) with a 1-byte threshold load (u8 path) in `uf_final` only. Rough ceiling: up to ~1/3 of `uf_final` (0.091-0.129 ms) plus a share of `label_pixels` (0.116-0.195 ms) - order 0.03-0.07 ms on Mali, i.e. ~1-2% of the GPU phase; also removes ~1/3 of `uf_final`'s atomic issues, the cost the G610 counter guide calls "multi-cycle per thread". Unmeasured.
- Accuracy / determinism impact: bit-identical under `min_cluster_pixels >= 2` (the label of a size-1 root is 0 either way; `blob_size` has no other reader - uf_final's own comment says label_pixels is its only reader). The stored `blob_size[i]` for 127 pixels becomes 0 instead of 1, which nothing observes.
- Applicability to vkapriltag: Both devices (scalar path everywhere; on RDNA the gain is smaller since the whole `uf_final` is ~0.03 ms). Requires `uf_final` to bind the thresholded buffer (both u32 and u8 variants, like `label_pixels`). Bound cheaply: dump the thresholded image once and count the 127 fraction at dec 2 on the test images - the ceiling is proportional to it; then ABBA the two spans. Not in the rejected list (it is not a pass fusion and not a subgroup construct).
- Verification: [verified from primary source] for the code path and the 153,886-root figure; uplift is my estimate

## Conclusions

Ranked by (expected value) / (cost to test). Every idea below is bit-identical by construction (integer min/max/sum folds are exact and order-free; layout and copy choice never change the folded result) unless stated. All respect the no-forward-progress rule (Sorensen OOPSLA21: ARM fails even LOBE): nothing waits on another invocation of the same dispatch.

1. **Take one Mali counter capture of `reduce_extents_hash` first.** On the G610, the documented counters that matter are `LoadStoreUnitCyclesAtomicAccess` / `ExecutionCoreActive` and `LoadStoreL2ReadBeats`. There is no public L1-snoop counter on the G610 (guide rev 1.7). A high atomic-cycle share means the span is *issue-bound*, so go to ideas 2 and 3. L2 read beats far above the tens-of-KB working set mean line migration, so go to ideas 4 and 5. Uplift: none directly; it decides which extents ideas are live. Device: Mali. Cost: one Streamline or libGPUCounters session.
2. **Pack `gx_sum`/`gy_sum` into one biased int64 `atomicAdd`** (in-tree entry). Add `((gy+1)<<32) | (gx+1)`, then subtract `count` in `select_blobs`. No carries, because 2 x 2,061,616 < 2^32. In-tree A8 rejected only the 32-bit form and said "a 64-bit atomicAdd has the width but needs int64 atomics". That variant has since shipped, so the blocker is gone. It removes the second atomic from every diagonal boundary point, taking the guard-surviving atomics from about 2.5 to about 2 per point. The analogous count+pxgx packing gave -12 to -13% of the extents span, so expect a similar order: roughly 0.02-0.03 ms on Mali. Determinism: none, as long as `select_blobs` knows which variant produced the sums. Device: Mali (int64 path). Bound: tally the diagonal-point fraction from one frame's `compacted[]`.
3. **Keep 127 (ambiguous) pixels out of `blob_size`** (in-tree entry). In `uf_final`, return early for code 127. In `label_pixels`, set label 0 for them without loading `blob_size`. This is exact when `min_cluster_pixels >= 2` (default 24). About a third of decimated pixels are singleton roots (153,886 at 1080p dec 2 per OPTIMIZATION_NOTES section 3). Their `blob_size` traffic is streaming, so it is the DRAM-proportional part of both spans (2.66x and 3.12x DMC sensitivity), and it also drops about a third of `uf_final`'s atomics. Expected: roughly 0.03-0.07 ms on Mali (1-2% of the GPU phase); small on RDNA. Bound: count the 127 fraction in one dumped threshold image, then ABBA the two spans.
4. **Lane-interleaved copy selection in `reduce_extents_hash`** (Henriksen SC20, Gomez-Luna). Use `copy = gl_LocalInvocationID.x & 7` instead of `gl_WorkGroupID.x & 7`. Boundary points arrive coherently, so today a whole workgroup hits one blob in one copy. Futhark measured 2-3x from this axis on NVIDIA. On Mali the result depends on whether the LSU already serializes per thread (if issue-bound, this does nothing). Expected: 0 to about 0.1 ms of the 0.221 ms span. Device: Mali scalar path. Cost: a one-line change plus ABBA at dec 1 and dec 2.
5. **Per-shader-core copies via `VK_ARM_shader_core_builtins`** (Arm BP section 10.13 prescribes per-core atomic variables; the extension is exposed by libmali 24.0.0, libmali 54.2.0 and panvk). **Do not use `gl_CoreIDARM & 7` directly**: the G610's `shaderCoreMask` is 0x50005, i.e. cores 0/2/16/18. Map with `bitCount(mask & ((1u<<id)-1u))`, and optionally add a lane or warp bit (`coreIdx*2 + (lane&1)`) to reuse the K=8 buffers. This keeps each copy's lines in one core's L1. Expected: unknown, since Arm gives no numbers; it targets the ~0.16 ms extents residual. The same trick applies to `uf_final`'s large-blob counters and to append counters. Device: Mali, as an optional extension path. Bound: idea 1's L2-read-beat proxy, then an A/B against idea 4.
6. **De-alias the private-copy stride** (PLOS25). All 8 copies of a blob are exactly 128 KiB apart, so their low 17 address bits are identical. Try a non-power-of-two stride (`(c-1)*(4096+9)`), and separately 64-byte padding of the private copies (Arm: one atomic per line). The K=8/16/32 plateau (-20.3/-20.0/-20.6%) fits either aliasing or issue-boundness. Expected: small to moderate, and only if Mali slice or atomic-unit selection uses low address bits (unknown). McKee's AMD/Intel data show padding is *not* automatically a win on GPUs, so measure it. Device: Mali. Cost: a 3-line change.
7. **CPU/NEON preprocessing offload on RK3588** (frc971 commit 922568c79: "The GPU was too full, this moves it back to the CPU"; 3x over the libapriltag CPU code; tested equal to CUDA). A spare A76 core writes `decimated` and `thresholded` straight into unified memory, and the GPU starts at `uf_init`. This removes four GPU passes and their barriers; an older dec-1 build recorded decimate+threshold at 0.86 ms of Mali GPU time. It is exact, and throughput-neutral-to-positive if run as a pipeline stage (+1 frame latency). Risks: shared LPDDR bandwidth, cache maintenance, and frc971's code being hard-wired to decimation 2. Device: Mali/RK3588 only. Bound: time frc971's `ThresholdAndDecimate` on one pinned A76 at 1280x800 against the sum of the four GPU spans.
8. **G610 atomic microbenchmark** (McKee/Epiphron-style: contention 1..256 x stride 4 B..8 KiB, power-of-two versus not). No public Valhall atomic curve exists: McKee lists mobile as future work, PLOS25 covers AMD/NVIDIA only, and Chips and Cheese covers Bifrost G52 only, qualitatively. It would settle ideas 4-6 before building them. Cost: a ~50-line Vulkan compute shader.
9. **RDNA: DISTWAR-style hybrid threshold in `reduce_extents_hash_subgroup`.** Aggregate only when at least X lanes share the key, otherwise use plain atomics. The shipped variant aggregates unconditionally (but already batches all 8 fields per key, which DISTWAR shows is the part that matters). Small absolute gain (RDNA is 0.66 ms in total). Sweep X over {2,4,8,16}.
10. **`hash_group` key-in-slot 64-bit CAS** (WarpCore packed CAS). Empty = 0 is safe because `rep0 != rep1`. It removes the dependent `keys[owner]` load but doubles the table clear. Low priority. First bound it with an incorrect build that accepts the first probe; build only if that ceiling is at least 0.03 ms. Epoch-tagging to skip the table clear is worth at most about 0.01 ms, so skip it.

**Confirmed optimal or not worth pursuing** (multiple independent sources):
- `hash_group` open addressing with linear probing and a single CAS on the owner index, at 1-2% load. SlabHash, WarpCore, WarpSpeed, BGHT, Karnagel and Lessley all differentiate only at high load. Cuckoo and Robin Hood move keys, which breaks owner-index slots and needs locks or rebuilds, and those are unsafe without forward progress (OOPSLA21). Hash beats sort far below ~2^14-2^17 groups (Karnagel, Futhark, Wu SIGMOD25); vkapriltag has 400-1300.
- Warp or subgroup aggregation of bare counters loses in two cases: when hardware already coalesces same-address atomics (NVCC >= 9; AMD and NVIDIA units absorb 32 flat per PLOS25), and on Mali, where subgroup ops are slow. Per-parameter warp reductions lose even on NVIDIA (DISTWAR: CCCL about 20% slower). This matches the in-tree rejections.
- Adaptive-threshold alternatives (Sauvola, Niblack, Bradley, integral images, OpenCV mean-C) all change the output and so fail bit-identity. They also cost more than AprilTag's 16x-downsampled block min/max. OpenCV has no OpenCL or CUDA adaptiveThreshold kernel to borrow (checked `thresh.cpp`, `cudaimgproc.hpp`, `cudaarithm.hpp`). The only threshold-stage lever found is *where* it runs (idea 7), not *how*.
- Adreno (not a target) has real local-memory atomic engines, so tile-local privatization might win there. Keep the extents strategy selectable per device.

**Determinism watch-item.** `raw_blob_counter` (hash_group dense ids) and the `blob_diff` append order are scheduling-dependent. Bit-identity relies on every consumer being order-insensitive; Wu et al. SIGMOD25 flag the same hazard. Any tie-break by index, or any capacity truncation, would expose it. Ideas 2, 3 and 10 do not touch it.
